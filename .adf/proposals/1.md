## 3. 資料與狀態

| 狀態 | 擁有者 | 誰改 | 執行緒 |
|---|---|---|---|
| `PackMLMachine` 各欄位、上次的 request 值（邊緣偵測）、blocked 旗標、Execute 進入時間、待完成旗標 | `ServiceHost`（每個 module、每個 bound service 各一份） | `Scan`、`Complete`、`Abort` | Scan 在 hosted node 的背景 task；`Complete`、`Abort` 在 workflow run 的 task。`ServiceHost` 用一個 `Lock` 保護全部狀態 |
| 上次寫出的 Status 欄位值 | `ServiceHost` | `Scan`，只在值改變時呼叫 `ProcessImage.WriteValue(..., WriteSource.Workflow)` | 同上 |
| hosts（含所屬 workflow 名稱）、overrides：以 (workflow, Ctrl 路徑) 為鍵，各有一個 token 物件。`SetOverrides(w, paths)` 只換掉 workflow w 的項目，並為 w 的每個路徑建立新 token。`OverrideToken(path)` 回傳最後一次 `SetOverrides` 涵蓋該路徑的 workflow 的 token（後載入者生效）；該 workflow `SetOverrides(w, [])` 後，改回其他仍涵蓋該路徑的 workflow 的 token。所有路徑查詢用 `StringComparer.OrdinalIgnoreCase` | `ServiceHostRegistry`（每個 `FlowRuntime` 一份） | hosted node 開始與結束時 `Register`、`Unregister`；`FlowRuntime.Load`、`Unload` 呼叫 `SetOverrides` | 用一個 `Lock` 保護。`Register` 取代舊 host 時，在 registry lock 外呼叫舊 host 的 `Retire()` |
| 每個 service 的 `ExecuteGeneration`、進入 Execute 時記下的 override token | `ServiceHost` | `Scan` | 同 `ServiceHost` 的 `Lock` |
| busy run 的 key | `LoadedWorkflow.BusyTriggers` | `StartRun`，key 改成 `$"{trigger.Id}#{busyKey}"`；`onServiceExecute` 的 busyKey 是 `"{index}:{generation}"` | 不變（`ConcurrentDictionary`） |

Override 判斷：service 進入 Execute 時記下 `overrideToken(ctrlPath)`。之後每個 scan，只有「記下的 token 不是 null，且等於 registry 目前的 token」才算 overridden。所以：
- 覆寫 workflow 在 service 停在 Execute 時被卸載或重新載入（token 改變），下一個 scan 改用預設行為，等待時間從進入 Execute 起算。
- 覆寫 workflow 在 service 已經在 Execute 時才載入，這次 Execute 不算 overridden，照預設行為完成；下一次進入 Execute 才由覆寫 workflow 處理。

`ServiceHost.Scan` 內呼叫 `ProcessImage.Write` 時會同步觸發 `Written`。目前唯一的訂閱者是 `FlowRuntime.cs:28` 的 `_writes.Writer.TryWrite`。新增的訂閱者不可以回呼 `ServiceHost`，否則會在 host lock 內重入。

Workflow 重新載入（Editor 存檔）：新的 `service.host` 在 `RunAsync` 開始時呼叫 `Registry.Register(workflow, host)`。同一個 workflow 已有舊 host 時，registry 先呼叫舊 host 的 `Retire()`（等舊 host 正在跑的 scan 結束，之後舊 host 不再寫 image），再重新取得 registry lock，再次檢查該 root 仍由同一個 workflow 持有後才換成新 host；檢查失敗時丟 `InvalidOperationException`。然後新 host 呼叫 `Initialize`：所有 bound service 回到 Idle，所有 module 回到 Execute。舊 task 收到取消後在 `finally` 呼叫 `Unregister(oldHost)`；它已不是註冊中的 instance，所以不做任何事。

## 4. 行為

### 4.1 `PackMLMachine.Scan`（對照 `FW/POUs/30_PackML_Base/FB_PackMLBase.TcPOU`）

每次呼叫依序執行：

1. `CommandRequest` 為 FALSE：清除 `CommandAccepted`、`CommandRejected`，`StateErrorId := NoError`，清除 command consumed 旗標。`ModeRequest` 為 FALSE：清除 `ModeChanged`、`ModeChangeRejected`，`ModeErrorId := NoError`，清除 mode consumed 旗標。
2. Mode：`ModeRequest` 為 TRUE 且未 consumed 時，標記 consumed，再依序檢查。第一個失敗的條件就拒絕：設 `ModeChangeRejected := TRUE` 和對應的 `ModeErrorId`。全部通過就接受：`PreviousMode := Mode`、`Mode := 新值`、`ModeChanged := TRUE`。
   - Mode 不是 0、1、2：2001。
   - Mode 等於目前的 Mode：2002。
   - State 不是 Aborted、Stopped、Idle、Complete：2003。
3. 選命令：有 queued 命令就取它並清空 queue；否則 `CommandRequest` 為 TRUE、`Command` 不是 0、且未 consumed 時，取 `Command`，並標記 consumed。
4. 分派：命令值不在 1 到 9 之間時，什麼都不設。命令值在 1 到 9 之間時，查下表。允許就設 `CommandAccepted := TRUE` 並換到目標狀態；不允許就設 `CommandRejected := TRUE` 和 `StateErrorId`，狀態不變。

| 命令 | 允許的來源狀態 | 目標 | 拒絕碼 |
|---|---|---|---|
| Clear | Aborted | Clearing | 1002 |
| Reset | Stopped、Complete | Resetting | 1003 |
| Start | Idle | Starting | 1004 |
| Stop | Starting、Idle、Execute、Completing、Complete、Holding、Held、Unholding、Suspending、Suspended、Unsuspending | Stopping | 1005 |
| Hold | Execute | Holding | 1006 |
| Unhold | Held | Unholding | 1007 |
| Suspend | Execute | Suspending | 1008 |
| Unsuspend | Suspended | Unsuspending | 1009 |
| Abort | Aborting、Aborted 以外的所有狀態 | Aborting | 1010 |

5. State hook：目前狀態是 acting state 時，呼叫一次 `isActingStateDone(State)`。回傳 TRUE 就換到下表的目的狀態。每個 scan 最多一次 hook 轉換。

| Acting state | 目的狀態 |
|---|---|
| Undefined | Aborted |
| Clearing | Stopped |
| Starting | Execute |
| Execute | Completing |
| Completing | Complete |
| Resetting | Idle |
| Stopping | Stopped |
| Aborting | Aborted |
| Holding | Held |
| Unholding | Execute |
| Suspending | Suspended |
| Unsuspending | Execute |

換狀態只在新狀態和目前狀態不同時執行：`PreviousState := State; State := 新狀態`。

`RequestCommand`：已有 queued 命令或 `modeRequestHigh` 為 TRUE 時回傳 FALSE；否則存入 queue 並回傳 TRUE。

### 4.2 Module 外形與探索（`ServiceHost` 建構子）

1. `root` 的型別是一維 `ArrayType` 時，每個元素是一個 module，index 取陣列範圍；是 `StructType` 時，只有一個 module，index 為 null。其他型別：`ServiceHostException`。
2. 每個 module struct 必須有 `ModuleCtrl`（型別名 `ST_ModuleCtrl`）、`ModuleStatus`（`ST_ModuleStatus`）、`ServiceCtrl`、`ServiceStatus` 四個成員。缺任何一個：`ServiceHostException`，訊息寫出缺的成員和 module 路徑。
3. 在 `ServiceCtrl` 底下深度優先走訪 struct 成員和一維陣列元素，型別名為 `ST_ServiceCtrl` 的節點就是一個 service。它的相對路徑 `rel`（例：`Shutter.Open`、`Arm[1].Lift.TopPos`）在 `ServiceStatus` 底下必須解析得到型別名 `ST_ServiceStatus`；解析不到就丟 `ServiceHostException`。
4. `identities.Find(rel)` 回傳的 `ServiceId` 不是 0，這個 service 就 bound；是 0 或找不到就不 bound。Polar2 的 145 個 identity 呼叫都用 `E_PolarIIChamberServiceId` 的成員，而該 enum 沒有值為 0 的成員，所以每個 module bound 145 個 service。
5. 全部 module 都沒有 bound service：`ServiceHostException("No service under <root> has a ServiceId.")`。

### 4.3 `ServiceHost.Initialize`

每個 module：
1. module 的 `PackMLMachine` 以 (Execute, Starting) 建立。
2. 以一次 `Write` 寫出 `ModuleStatus.ResponseId` 到 `ModuleStatus.PackMLOut` 結尾的整段：ResponseId 0，PackMLOut 取 machine 的初始值（eStateCurrent Execute、eStatePrevious Starting，其他 0 或 FALSE）。
3. 用這段的值當 last-written cache 的起始值。
4. `SeedInput(目前的 ModuleCtrl 輸入)`，並把邊緣偵測的「上次值」設成目前的 request 值。

每個在 identity table 裡的 service（bound 和不 bound 都算）：
- `ServiceStatus.<rel>.ServiceId := ServiceId`、`CompletionBehavior := CompletionBehavior`。不 bound 的 20 格也寫這兩個欄位。

每個 bound service：
1. 它的 `PackMLMachine` 以 (Idle, Resetting) 建立。
2. 以一次 `Write` 寫出 `ResponseId` 加整個 `PackMLOut`：ResponseId 0，eStateCurrent Idle、eStatePrevious Resetting，其他 0 或 FALSE。
3. 用這段的值當 cache 的起始值。
4. `SeedInput(目前 client 的 Ctrl 輸入)`，邊緣偵測的「上次值」設成目前的值。所以重載時 client 一直保持 TRUE 的 request 不會再執行一次。
5. `ExecuteGeneration` 為 0（表示尚未進入 Execute；計數器本身不重設）。

不 bound 的 service 不寫 `ResponseId` 和 `PackMLOut`，保持 image 原值（啟動時為 0，也就是 eStateCurrent Undefined），和真 PLC 沒有 FB 時相同。

### 4.4 `ServiceHost.Scan`（對照 `FW/POUs/10_Module/FB_ModuleBase.TcPOU`、`FB_ServiceCoordinator.TcPOU`、`FW/POUs/20_Service/FB_ServiceBase.TcPOU`）

欄位對應（service 和 module 相同）：

| DUT 欄位 | C# |
|---|---|
| `PackMLIn.eCommand` | `PackMLInput.Command` |
| `PackMLIn.bCommandChangeRequest` | `PackMLInput.CommandRequest` |
| `PackMLIn.eMode` | `PackMLInput.Mode` |
| `PackMLIn.bModeChangeRequest` | `PackMLInput.ModeRequest` |
| `PackMLOut.eStateCurrent` | `PackMLMachine.State` |
| `PackMLOut.eStatePrevious` | `PreviousState` |
| `PackMLOut.eModeCurrent` | `Mode` |
| `PackMLOut.eModePrevious` | `PreviousMode` |
| `PackMLOut.bCommandAccepted` | `CommandAccepted` |
| `PackMLOut.bCommandRejected` | `CommandRejected` |
| `PackMLOut.eStateErrorID` | `StateErrorId` |
| `PackMLOut.bModeChanged` | `ModeChanged` |
| `PackMLOut.bModeChangeRejected` | `ModeChangeRejected` |
| `PackMLOut.eModeErrorID` | `ModeErrorId` |
| Ctrl 的 `RequestId`、Status 的 `ResponseId` | 本節第 4.2 步、第 5 步 |

`ResponseId` 和 `PackMLOut` 在 `ST_ServiceStatus` 中相連（ResponseId offset 0，PackMLOut offset 4）；在 `ST_ModuleStatus` 中也相連（ResponseId 緊接在 PackMLOut 前）。實作者在建構時用 `SymbolTable.Resolve` 算出起點和長度，並檢查兩者相連；不相連就丟 `ServiceHostException`。

每個 module 依序執行：

1. 用一次 `ProcessImage.Read` 讀 `ModuleCtrl`、一次讀整個 `ServiceCtrl`，再用 `ValueCodec.Decode(欄位型別, 切片)` 解出欄位。欄位的相對 offset 在建構時算好。
2. Module 的 `PackMLMachine.Scan`。`isActingStateDone` 的規則：
   - 「上一個 scan 的 service 狀態」在 `Initialize` 之後的第一個 scan 取 `Initialize` 設定的狀態（全部 Idle）。
   - Clearing、Stopping：上一個 scan 所有 bound service 都在 Stopped。
   - Resetting：上一個 scan 所有 bound service 都在 Idle。
   - Aborting：上一個 scan 所有 bound service 都在 Aborted。
   - Execute：永遠 FALSE。
   - 其他 acting state：TRUE。
3. `moduleInExecute := module.State == Execute`（取轉換後的狀態）。
4. 每個 bound service 依序執行：
   1. **算出 effective 輸入。**
      - `moduleInExecute` 為 FALSE：
        - effective RequestId 與整個 effective PackMLIn 都直接複製 raw `ModuleCtrl`（RequestId、eCommand、bCommandChangeRequest、eMode、bModeChangeRequest），與 module 是否接受該命令無關。
        - 接著，raw CommandRequest 為 FALSE，或 eCommand 不是 Stop、Abort、Clear、Reset 時：Command := 0、CommandRequest := FALSE。依據 `FW/POUs/10_Module/FB_ServiceCoordinator.TcPOU:331-344`。
        - client 自己的 CommandRequest 為 TRUE 時，設 command blocked 旗標；ModeRequest 同理，設 mode blocked 旗標。
      - `moduleInExecute` 為 TRUE：
        - 用 client 的 Ctrl。
        - command blocked 旗標成立時，client 的 CommandRequest 為 FALSE 就清除旗標；旗標還在時，effective CommandRequest := FALSE。mode blocked 旗標同理。
   2. **ResponseId。** effective CommandRequest 由 FALSE 變 TRUE（和這個 service 上一個 scan 的 effective 值比）時，寫 `ResponseId := effective RequestId`。不論命令之後被接受、拒絕或是未知值都寫。
   3. **PackMLMachine.Scan。** `isActingStateDone` 的規則：
      - Execute：
        - 這次 Execute 算 overridden（第 3 節的 token 規則）：只看待完成旗標。旗標成立時清除旗標並回傳 TRUE；不成立時回傳 FALSE，不看等待時間。
        - 不算 overridden，且 CompletionBehavior 為 NaturalCompletion：`now - 進入 Execute 的時間 >= defaultDelay` 時回傳 TRUE，否則 FALSE。
        - 其他情況回傳 FALSE。
        - 從 Unholding、Unsuspending 回到 Execute 也算一次新的進入：generation 換新、等待時間重新計算、`onServiceExecute` 再觸發一次。
      - 其他 acting state：TRUE。
   4. 這個 scan 內狀態變成 Execute 時：記下 `now` 為進入 Execute 的時間，從全程序共用的計數器（`Interlocked.Increment`）取一個新值作為 `ExecuteGeneration`，記下 `overrideToken(ctrlPath)`，清除待完成旗標。
   5. `ResponseId` 或 `PackMLOut` 任一欄位和 cache 不同時，以一次 `Write`（`WriteSource.Workflow`）寫出 `ResponseId` 加整個 `PackMLOut`，並更新 cache。client 用 Read 輪詢時不會讀到只更新一半的狀態。
5. Module 的 ResponseId：raw `ModuleCtrl` 的 CommandRequest 或 ModeRequest 有上升緣時，寫 `ModuleStatus.ResponseId := ModuleCtrl.RequestId`。
6. Module 的 `ResponseId` 或 `PackMLOut` 有改變時，以一次 `Write` 寫出 `ModuleStatus.ResponseId` 到 `PackMLOut` 結尾的整段。

已知時間窗（接受，不處理）：
- `Complete` 只設旗標，到下一個 scan 才離開 Execute。這段最多一個 scan（約 10 ms）內若 client 送 Stop 或 Abort，命令先處理，service 不會 Complete，但 workflow 已經寫了 SVID。
- `Complete` 之後、下一個 scan 之前若覆寫 workflow 被重新載入，token 改變，這次 Execute 改回預設行為，旗標被忽略。
- `trigger.onServiceExecute` 在 dispatch 執行緒讀取 generation，可能讀到更新的值；結果仍是目前這次 Execute 只被完成一次。

`Complete(ctrlPath, generation)` 要求：service 是 bound、狀態是 Execute、這次 Execute 算 overridden、`generation` 為 null 或等於 `ExecuteGeneration`。成立時設待完成旗標，下一個 scan 由 Execute 轉到 Completing。

`Abort(ctrlPath, generation)`：`generation` 不是 null 且不等於 `ExecuteGeneration` 時丟 `InvalidOperationException`。否則呼叫 `PackMLMachine.RequestCommand(Abort, 該 service 目前的 effective ModeRequest)`，下一個 scan 處理。傳 ModeRequest 是照抄 `FB_PackMLBase.RequestCommand`：mode request 為 TRUE 時不接受內部命令。RequestCommand 回傳 FALSE 時丟 `InvalidOperationException`，該次 run 失敗並在 Editor 顯示。

### 4.5 節點

- **`service.host`**
  - Create：
    1. 解析 `root`。
    2. 讀 `ProjectFile(identityFile)`，用 `ServiceIdentityTable.Parse` 解析；enum 名稱由 `SymbolTable.TryGetEnumValue` 解析。
    3. 建立 `ServiceHost`，`overrideToken` 傳 `path => _registry?.OverrideToken(path)`。
    4. 任何 `ServiceHostException`、`ServiceIdentityException`、找不到檔案，都轉成 `NodeConfigurationException`，成為 workflow diagnostic（AC13）。
  - RunAsync：
    1. `_registry = context.Registry`；`Registry.Register(context.Workflow, host)`（同一 workflow 的舊 host 先被 `Retire`，第 3 節）。
    2. `Initialize`。
    3. 記下 `start = TimeProvider.System.GetTimestamp()`，用 `PeriodicTimer(ServiceHost.ScanInterval)` 迴圈呼叫 `Scan(image, TimeProvider.System.GetElapsedTime(start))`，直到取消。`Scan` 丟出的例外不在迴圈內攔截：迴圈結束，hosted node 發布 `RunFailed`（NodeId 為該節點、Error 為例外訊息），Editor 顯示錯誤；重新存檔該 workflow 即重新啟動。
    4. `finally` 裡 `Unregister`。
  - Registry 在 Create 時還拿不到（`NodeSettings` 不帶 registry），所以節點有一個 `ServiceHostRegistry? _registry` 欄位，RunAsync 開始時設 `_registry = context.Registry`。在這之前 `Initialize`、`Scan` 都還沒執行，不會讀到 null。
- **`trigger.onServiceExecute`**
  - Create：
    1. `IndexedSymbol.Parse(service, scalar: false)`，型別名必須是 `ST_ServiceCtrl`。
    2. 路徑中必須含 `.ServiceCtrl.`（不分大小寫），把第一個出現處換成 `.ServiceStatus.` 得到 Status 範本，再接 `.PackMLOut.eStateCurrent`。
    3. `ResolveAll` 取得每個 index 的 eStateCurrent symbol，以及對應的 Ctrl 路徑清單 `CtrlPaths`。
  - 實作 `IRegistryAware`；`Attach` 存下 registry。
  - `CtrlPaths`：對 `service` 範本的 `IndexedSymbol` 呼叫 `ResolveAll`，與 eStateCurrent 的清單依 index 對齊。
  - TryFire：不過濾 `WriteSource`（Execute 本來就由 host 以 `WriteSource.Workflow` 寫入）。write 和其中一個 eStateCurrent symbol 重疊，且這次寫入後的值是 6（Execute）、寫入前不是 6。依 `ResolveAll` 的順序取第一個符合的 symbol。outputs：`index`（未用 `[#]` 時為 null）、`generation`（`registry.FindByService(ctrlPath)?.ExecuteGeneration(ctrlPath)`，找不到 host 時為 null）。
  - `BusyKey`：`$"{index}:{generation}"`。所以同一個 service 的新一次 Execute 不會被舊 run 擋住；舊 run 醒來後呼叫 `completeService` 時 generation 不符，丟例外，該 run 失敗，不影響新的 Execute。
- **`action.completeService`、`action.abortService`**
  - `service.Resolve(Symbols, Input("index"))` 得到 Ctrl 路徑（一律用 `SymbolRef.Path`，與 host 走訪型別樹得到的路徑字串相同）。`generation` 輸入為 null 時不檢查，否則以 `PlcValue.ToInt64` 轉型後傳給 `Complete`、`Abort`。
  - `Registry.FindByService(path)` 為 null：丟 `InvalidOperationException("No service.host runs <path>.")`。
  - 否則呼叫 `Complete` 或 `Abort`。
  - 例外讓這次 run 失敗，Editor 顯示錯誤（`FlowRuntime.cs:120-129`）。
- **`trigger.onStart`**：`FlowRuntime.Load` 成功後，對每個 `StartTriggerNode` 呼叫一次 `StartRun`，outputs 為空字典。
- **`FlowRuntime.Load`**
  1. 編譯。
  2. 換掉舊版本：`previous.Stop()`。
  3. 對每個 `IRegistryAware` 節點呼叫 `Attach(Registry)`；`Registry.SetOverrides(name, 所有 onServiceExecute 節點的 CtrlPaths)`。
  4. 啟動 cyclic triggers、hosted nodes、start triggers。
  - hosted node 以 `HostedNodeContext(image, Registry, name)` 啟動；例外（`OperationCanceledException` 除外，包括 `Register` 因其他 workflow 佔用 root 而丟出的例外）發布 `FlowEventKind.RunFailed`，NodeId 是該節點、Error 是例外訊息。`LiveHub.Publish` 對每個 `RunFailed` 事件寫一筆 warning log（`LiveHub` 新增 `ILogger<LiveHub>` 建構參數，由 DI 注入），所以沒開 Editor 也看得到。
  - `LoadedWorkflow` 保存 hosted task。`DisposeAsync` 在取消後 await 全部 hosted task，所以測試 dispose runtime 後讀 image 不會和最後一次 Scan 競爭。
- **`FlowRuntime.Unload`**：`Registry.SetOverrides(name, [])`。

### 4.6 `[#]` 規則（`IndexedSymbol`）

1. 路徑中 `[#]` 出現 0 次：等同一般 symbol，`IsIndexed` 為 FALSE，`index` 被忽略。
2. 出現 2 次以上：`NodeConfigurationException("Only one [#] is allowed.")`。
3. 出現 1 次：`[#]` 前面的路徑必須解析成一維 `ArrayType`，否則丟 `NodeConfigurationException`。把 `[#]` 換成陣列下限後解析整條路徑；`scalar` 為 TRUE 時，結果必須是 scalar。
4. `Resolve`：index 以 `PlcValue.ToInt64` 轉型（long、int、double、數字字串都可）。
   - `IsIndexed` 為 TRUE 且 index 為 null：`InvalidOperationException("<template> needs input 'index'.")`。
   - index 超出上下限：`InvalidOperationException("Index <i> is outside <lower>..<upper> of <template>.")`。
5. `ResolveAll`：`IsIndexed` 為 FALSE 時回傳一筆，index 為 null；否則從下限到上限各一筆。

### 4.7 `ServiceIdentityTable.Parse`

- 先去掉開頭的 BOM 與空白；之後以 `<` 開頭時當作 TwinCAT XML，取第一個 `<ST>` 元素的文字；否則整段當作 ST。
- 先移除 `//` 到行尾和 `(* … *)` 註解，再以 `;` 切成敘述。
- 只認兩種敘述，其他一律忽略：
  1. `F_<任意識別字>(Status := ServiceStatus.<rel>, ServiceId := <Enum.Member>, CompletionBehavior := <Enum.Member>)`。三個具名參數順序不限。
  2. `ServiceStatus.<rel>.CompletionBehavior := <Enum.Member>`。
- `<rel>` 去掉 `ServiceStatus.` 前綴，比對時不分大小寫。
- enum 名稱解析不到：`ServiceIdentityException("Unknown enum value '<name>'.")`。
- 同一個 `<rel>` 出現兩次：逐欄位後者覆蓋前者。第 1 種敘述寫 ServiceId 和 CompletionBehavior；第 2 種只寫 CompletionBehavior，保留先前的 ServiceId（沒有先前值時為 0）。

## 8. 考慮過的做法

從 issue 複製：
- 每個 service 一張 workflow：數量上千，PackML 邏輯重複。
- 直接執行 framework 的 ST：模擬器沒有 ST 執行器。
- 用腳本從 xlsx 產生 flow.json：PackML 邏輯複製多份。
- `ProjectPath` 直接指向 Polar2 repo：Polar2 repo 沒有 library 型別宣告。
- 沿用簡化的 `FrameworkLibrary.st`：版面與真 PLC 不同。
- 以 `E_PolarIIChamberTargetMode` 解讀 TargetMode：Allen 說明本案不使用該 enum。

寫 proposal 時新增：
- **事件驅動（每次 client write 才處理）**：framework 的上升緣、命令只處理一次、回到 Execute 時的 blocked 規則都以 scan 定義；事件驅動要另外重建這些語意。改用 10 ms scan。
- **`[#]` 以外的兩種做法（issue #1 決策紀錄：Allen 選 `[#]`）**：(b) 相對路徑節點，編譯時無法驗證路徑；(c) 每個 module 複製一份 workflow，需要 12 份。
- **用 `MemoryTriggerNode` 監看 client 寫入來驅動 PackML**：PackML 的上升緣、命令只處理一次、blocked 旗標、module 等待 service 都以 scan 定義，需要在固定週期讀全部輸入；trigger 只在有寫入時執行，無法表達「上一個 scan 的 service 狀態」。改用 hosted node 自己的 scan 迴圈。`trigger.onServiceExecute` 只負責通知覆寫 workflow，不驅動 PackML。
- **只複製 framework 型別的封閉集合**：要另寫相依分析，複製全部 104 個 DUT 已經驗證可行（主張 1），多出的型別不佔 process image。
- **讓 `service.host` 也寫 SVID**：issue #1 範圍規定 SetMode、Initial 由 workflow 寫 SVID。
- **把 identity 值抄成 C# 或 JSON**：會多一份要同步的資料；直接解析原始 TcPOU。

## 11. 風險

1. **Editor 能否顯示沒有任何 port 的節點**：`service.host` 沒有 inputs 和 outputs。`wwwroot/editor/editor.js` 不在 .NET 掃描範圍。Stage I 用瀏覽器開啟 `Polar2_ServiceHost` 確認。
2. **（已關閉）收集全部 enum 值可能讓舊專案建置失敗**：以前沒被使用的 enum 宣告不會被解析，現在會。若某個 enum 的 base type 不合法，`RobustSolutionDemo` 會在啟動時失敗。stage D 第 2 輪的 probe 為每個 enum 宣告一個變數：Polar2 加 FW 的 50 個、RobustSolutionDemo 的 9 個全部建置成功。
3. **ADS server 載入 12.7 MB、深層巢狀的 symbol**：`AdsTypeFactory` 從未處理過這麼大的型別樹。AC14 的 Ads 測試會實際啟動 server；它沿用 `tests/AdsPlcSimulator.Tests/Ads/AdsServerTests.cs` 的前提（本機 TwinCAT ADS router），沒有 router 時以 `ClientPortNotOpen` 失敗，依 `.adf/profile.md` 歸類為環境失敗。
4. **重新載入**：由 `Register` 取代並 `Retire` 舊 host 處理（第 3 節），舊 host 之後不再寫 image。測試 `Reloading_host_workflow_keeps_scanning` 涵蓋。
5. **Scan 負載**：每 10 ms 對 6 個 module 各讀兩次（32 bytes 和 3300 bytes），只在值改變時寫入。寫入會觸發 `Written` 事件，進入 `FlowRuntime` 的 channel。Stage H 量測 CPU；若超過單核 10%，再評估。
6. **framework 升級漂移**：C# 對照 1.0.0.4。升級時要人工比對 `FB_PackMLBase`、`FB_ServiceCoordinator`、`FB_ModuleBase`、`FB_ServiceBase` 的 diff（issue 決策紀錄）。
