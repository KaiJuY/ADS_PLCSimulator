## 2. Shape

### 2.1 U1：ECID 上下限（`src/AdsPlcSimulator.Host/Project/ModuleConfig.cs`）

```csharp
internal sealed record DescriptorConfig
{
    // existing: Id, Name, Unit, DataType
    public double? LowerLimit { get; init; }   // new
    public double? UpperLimit { get; init; }   // new
}
```

`ModuleConfigPublisher.DataTypes` 的值多一欄型別範圍：`(string EnumMember, string InitialValue, (double Lower, double Upper)? Range)`；DINT `(-2147483648, 2147483647)`、REAL `(-3.402823466E38, 3.402823466E38)`、BOOL 與 STRING `null`。

驗證（`ValidateList` 多一個參數 `bool isConfigParam`，`ValidateModule` 對 `variableList` 傳 false、`configParamList` 傳 true；在 `ValidateDescriptor` 之後呼叫新 private 方法 `ValidateLimits(DescriptorConfig item, bool isConfigParam, string where, string path)`，依序檢查、第一個違反就 `throw Fail(...)`；用 if 依序寫即可，不必做成表）：
1. `variableList`（SVID）有 `lowerLimit` 或 `upperLimit` → `"{where}: id {id}: lowerLimit/upperLimit are only for configParamList."`（SVID 的 `ST_ExtDescriptor` 沒有上下限欄位）。
2. 只有一個 → `"{where}: id {id}: lowerLimit and upperLimit must be given together."`（同 `FW:Configuration/POUs/FB_ModuleConfigurationManager.TcPOU:640-643`）。
3. BOOL、STRING 有上下限 → `"{where}: id {id}: BOOL and STRING must not declare limits."`（同 `:796-800`）。
4. `lowerLimit > upperLimit` 或任一超出型別範圍 → `$"{where}: id {id}: limits must satisfy lower <= upper within {Lower}..{Upper}."`（同 `:806-816` 與其後的型別範圍檢查）。非有限值在 JSON 解析時就失敗（`System.Text.Json` 不接受 `NaN`、`1e999`），走既有的 `invalid JSON` 訊息。DINT 的上下限可以有小數（framework 存成 LREAL，不檢查）。

發布（`AddDescriptor`，`isConfigParam` 時）：數值型 `HasLimits := TRUE`、`LowerLimit := item.LowerLimit ?? Range.Lower`、`UpperLimit := item.UpperLimit ?? Range.Upper`；BOOL、STRING `HasLimits := FALSE`、上下限不寫（留 0，同 `FW:POUs/10_Module/FB_ModuleBase.TcPOU:720-724` 只在 `HasLimits` 時發布）。

## 3. Data and state
- `ConfigParamService` 持有：batch 與 `ModuleConfigParamList` 的元素 layout（見 2.2）、active snapshot（`List<(int DataType, string Value, int MetadataIndex)>`）。snapshot 在 `Validate` 開頭清空、全部通過才填入；`Apply` 寫完清空；`Clear`（service reset）清空。所以失敗的 batch 與已寫入的 batch 都不會再被寫。
- `ServiceUnit.StartingChecked`、`StartingAbortPending`：只由 `ServiceHost` 在 scan 中讀寫。
- 全部在 `ServiceHost._lock` 之內、scan 執行緒上，與既有欄位相同（`ServiceHost.cs:27`）。
- 寫入的 `Value` 只存在 process image；重新 Run 由 `ModuleConfigPublisher` 重寫（D-Q12）。
- client 以 ADS 寫 batch 與 scan 不是原子的：scan 可能讀到寫到一半的 batch。framework 相同（`H_OnStarting` 在第一次 scan 複製 `Param`），接受。

## 4. Behavior

### 4.1 Starting（AC3、AC4）
`IsStartingDone(service, image, modeRequestHigh)`，一次呼叫內依序執行：
1. `service.ConfigParams` 為 null → 回傳 true（現狀）。
2. `!service.StartingChecked`：設 `StartingChecked = true`；`check = ConfigParams.Validate(image)`；`check.Passed` → 回傳 true。否則 `AddFrameworkError(service, image, check.MainErrorId, check.ParamId, check.Message)`、`StartingAbortPending = true`，**接著做第 3 步（同一次呼叫）**。
3. `StartingAbortPending`：`if (service.Machine.RequestCommand(Abort, modeRequestHigh)) StartingAbortPending = false;`
4. 回傳 false（留在 Starting）。

失敗時每次 scan 的狀態（mode request 為 low）：
- scan N：client Start → Idle → Starting；hook 驗證失敗、加錯誤、Abort 排入佇列；停在 Starting。
- scan N+1：「選命令」取出佇列的 Abort（Starting 允許 Abort）→ Aborting；Aborting 是動作狀態，hook 對非 Execute 回 true → 同一次 scan 到 Aborted。離開 Starting → `ResetStarting`。

mode request 一直為 high 時：每次 scan 重試 `RequestCommand`，service 停在 Starting，`ErrorList` 已有錯誤（client 看得到 alarm）。client 放開 mode request 後下一次 scan 排入；或 client 送 Stop（Starting 允許 Stop → Stopping → Stopped）或 Abort 離開，離開時 `ResetStarting`，snapshot 已是空的，不會寫入。

framework 在 `RequestCommand` 失敗時不重試：`H_OnStarting` 只在 `bFirstScan` 驗證並 `RequestCommand(Abort); RETURN;`；下一次 scan `bFirstScan` 為 FALSE，跳過驗證，往下做 `PersistentWriteCoordinator.M_Request`，得到 `Owned` 就回 Done → Execute，`H_OnExecute` 第一次 scan 以 `M_ApplyConfigParamBatch(_ActiveParam)` 寫入驗證失敗的 batch（`FW:POUs/20_Service/ConfigParam Service/FB_SetConfigParamService.TcPOU` `H_OnStarting`、`H_OnExecute`）。模擬器改為每次 scan 重試直到排入（同 #13 P1 A），失敗的 batch 不會寫入（AC3「沒有任何一筆寫入」）。

同一個 service 可能同時有 Alive 的待送 Abort（#13 P1 A，從 Execute 帶出來）：`ApplyAlive` 在 `Machine.Scan` 之前先排；佇列已滿時 `IsStartingDone` 的 `RequestCommand` 回 false，下一次 scan 再試。兩者都是 Abort，結果相同。

`Validate` 的規則（照 `FW:POUs/10_Module/FB_ModuleBase.TcPOU:946-1028`，逐筆、第一個錯誤就回傳）：
1. `batch[1].Id = 0` → EmptyBatch，ParamId 0。
2. 逐筆直到 `Id = 0` 或陣列結束；ParamId = 該筆 Id：
   1. 前面已有相同 Id → DuplicateId。
   2. `ModuleConfigParamList` 沒有 `Id` 相同的元素（只比對 `Id ≠ 0` 的元素）→ MetadataNotFound。
   3. 該元素 `IsBound` FALSE → NotBound。
   4. `batch.DataType ≠ ToConfigDataType(元素.DataType)`（元素為 DateTime 或未知值 → `ToConfigDataType` 為 null → 不相等；batch 的 DataType 為 0 或 > 10 也不會相等）→ DataTypeMismatch。
   5. `!IsStrict(value, dataType)` → InvalidValueFormat。
   6. 數值型（Boolean、String80 以外的 8 種）：`double.Parse(value, InvariantCulture)` 非有限 → InvalidValueFormat；`!IsInTypeRange` → OutOfRange；`< 元素.LowerLimit` 或 `> 元素.UpperLimit` → OutOfRange（不看 `HasLimits`，同 FW `:1020-1022`）。
3. 全部通過 → None。

`IsStrict`（照 `FW:POUs/20_Service/ConfigParam Service/F_IsStrictConfigParamValue.TcPOU`，實作時逐行對照該檔）：String80 長度 ≤ 80；Boolean 只接受 `TRUE`、`FALSE`；其他型別空字串不合法；有號整數（Integer8/16/32）與浮點可有一個前置 `+`/`-`，且其後必須還有字元；無號整數不可有符號；整數其餘字元只能是數字；浮點：尾數至少一個數字（在指數之前）、最多一個 `.`（在指數前）、`e`/`E` 須在已有數字之後且只能一次、指數後可有一個 `+`/`-` 緊接在 `e` 之後、有指數時指數須有數字。

`IsInTypeRange`：Integer8 −128..127、UnsignedInteger8 0..255、Integer16 −32768..32767、UnsignedInteger16 0..65535、Integer32 −2147483648..2147483647、UnsignedInteger32 0..4294967295、Float32 |v| ≤ 3.402823466E38、Float64 不檢查。

### 4.3 Execute（AC5、AC6）
- 進入 Execute 的那次 scan，`EnterExecute` 呼叫 `Apply`：對 snapshot 每筆，`ModuleConfigParamList[MetadataIndex].Value := Format(value, dataType)`。
- Hold、Suspend 後回到 Execute 不會再寫（snapshot 已清空）。
- 下一次 scan Execute 的 hook 回傳 true → Completing；再下一次 scan → Complete（stage F 更正：原寫「下一次 scan Complete」，Completing 是另一個 scan 的動作狀態）（不等持久儲存；不產生 928、929、930）。workflow 接管（`IsOverridden`）時由 workflow 決定完成時間，`Apply` 照做。
- `Format`：Boolean → 原字串（已驗證為 `TRUE`/`FALSE`）；String80 → 原字串；整數型 → `((long)double.Parse(v)).ToString(Invariant)`（去掉 `+`、前置 0；同 `LREAL_TO_DINT` 後 `DINT_TO_STRING`）；Float32 → `((float)double.Parse(v)).ToString("R", Invariant)`；Float64 → `double.Parse(v).ToString("R", Invariant)`。TwinCAT `REAL_TO_STRING`／`LREAL_TO_STRING` 的確切格式在 stage I 以 853 量測，不同時修正 `Format`。

### 4.4 Stop、Abort、Clear
- Starting 中收到 Stop 或其他命令：照現有 `PackMLMachine` 規則；離開 Starting 時 `ResetStarting`。
- `ErrorList` 由現有 Clearing 處理清除（`ServiceHost.cs` `PassedThroughClearingThisScan`）。

### 4.5 ECID 上下限（AC1、AC2）
見 2.1。Polar2 的 `module-config.json` 沒有上下限，所以 438 個 ECID 中數值型發布型別完整範圍；README 說明可手動加 `lowerLimit`/`upperLimit`，以及 `spec-to-config.py` 重新產生會覆蓋。

## 11. stage I：853 量測程序（AC9）
程式：`.adf/evidence/15/setconfig853/`（console，TwinCAT.Ads，`AmsNetId.Local`）。只接受 `--port 853` 或 `--port 25860`；其他 port（含 851、852）直接結束。853 用 `--root GVL_Module.Chamber1_Control[1]`，模擬器用 `GVL_Module.Chamber_Control[1]`。

寫入只限（D-R4，記憶 `real-plc-853.md`）：`ServiceCtrl.SetConfigParam.PackMLIn`（Start、Clear、Reset 命令）、`ServiceParam.SetConfigParam`（batch）、`ModuleCtrl.AlarmAckRequest`。模擬器端的 service 是 `ServiceCtrl.Chamber.SetConfig`。

步驟：
1. 讀 `ModuleConfigParamList` 全部，挑一個 DINT 與一個 REAL ECID（853 沒有 REAL 時只量 DINT，記錄 REAL 未量），記下 Id、Value、上下限、HasLimits。把原值寫到 `.adf/evidence/15/853-original.json`，**檔案寫成功才繼續**。讀 service 狀態，不是 Idle 就停止並回報。
2. 成功：batch = 挑選的 ECID，值取原值 +1（仍在上下限內）；Start；等到 Complete（逾時 5 s 停止）；讀回 Value 字串。REAL 另量 `"1.5"`、`"0.1"`、`"+2"`、`"1e2"` 的讀回字串（每個值一輪）。每輪之後 Reset → Idle。
3. 失敗（不寫入）：空 batch（920）、不存在的 Id 4294967000（922）、超出上限（926）。每輪：Start → 等到 Aborted → 讀 `ErrorList[1]` 與 `ModuleAlarmList` → Ack → Clear → Reset → 確認 Idle；確認該 ECID 的 Value 沒變。
4. 還原：batch = 原值 → Start → Complete → 讀回確認等於原值 → Reset。最後清空 batch（全寫 0）。
5. 程式中斷時：重新執行 `--restore`，從 `853-original.json` 寫回並讀回確認。
6. 模擬器以同一程式跑一次（ECID 318 與一個 REAL ECID），比對 MainErrorId、SourceErrorId、Message、最終狀態、Value 字串。`Format` 不同時修正並補測試。
