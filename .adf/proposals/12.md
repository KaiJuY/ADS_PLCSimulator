## 4. Behavior

### 每次 scan（AC1–4、14）
`ScanModule` 在現有 PackML 與 service 處理之後（`ServiceHost.cs:164-176` 的 `module.Status.Write` 之後），對有 `ModuleAlarmBlock` 的 module 依 framework `M_UpdateAlarmState` 的順序（FW: `POUs/10_Module/FB_ModuleBase.TcPOU:632-705`）執行：

1. `manager.BeginCycle(block.ReadModuleId(image))`。不在設定檔中的 module，`ModuleId` 為 0，alarm 照常運作（framework 沒有 ModuleId 0 的檢查）。ModuleId 改變時 manager 清空三個來源；`ErrorList` 內已寫入的舊 ModuleId 不改（同 framework，`ErrorList` 在 manager 之外），下一次 scan 以新的 latch 重新出現。
2. 對每個 configured alarm：`manager.SuppressHookAlarm(mainErrorId)`。
3. `manager.ProcessAcknowledgement(block.ReadAckRequest(image))`。
4. configured alarm：讀 source symbol、依 `AlarmSourceType` 轉成 double（BOOL → 1/0；整數、REAL、LREAL 直接轉；String80 → `sampleValid` FALSE），再呼叫 `UpdateConfiguredAlarm(i, valid, AlarmCondition.IsMet(...), snapshot, <本次 scan 的時間字串>)`。snapshot：`ModuleId`、`ServiceId` 0、`MainErrorId`、`SourceErrorId`、`Message`、`Severity`，`Path` = `<module path>.<source>`（FW: `FB_ModuleConfigurationManager.TcPOU:298-300`）。
   每次 scan 開始時只呼叫一次 `AlarmClock.Format(utcNow())`，步驟 4、5 共用這個字串。
5. hook alarm：依 `List<HookSubmission>` 的順序，對每一筆建立 `ExtAlarm`（`ModuleId` 0、`ServiceId` 0、`DateTime` = 本次 scan 的時間字串，其他欄位取自 submission，`Path` 空字串時用 module 路徑），呼叫 `ObserveHookAlarm`。manager 只在第一次 latch 時用這個 `DateTime`；再出現時保留第一次的 snapshot（framework `M_ObserveHookAlarm`），manager 在 latch 時蓋上 `ModuleId`。設定檔已有同一個 `MainErrorId` 時不提交（FW: `FB_ModuleBase.TcPOU:177-187`，ownership）。
6. service alarm：對每個 bound service（`BoundServices` 的順序，即 symbol 表順序；framework 是 service 註冊順序，多個 service 同時有 alarm 時 List 位置可能和真機不同，853 只比對欄位）的 `ErrorList` 中 `MainErrorId` ≠ 0 的每一筆呼叫 `ObserveServiceAlarm`（不看 entry 的 `Active`，FW: `POUs/10_Module/FB_ModuleBase.TcPOU:858-872`）。`ErrorList` entry 的 `Active` 永遠是 TRUE（`M_AddError` 寫入），沒有人改它；service alarm 變成 inactive 的唯一方式是 entry 從 `ErrorList` 消失（Clearing 清空），manager 在 `EndCycle` 把本 scan 沒看到的 latched service alarm 設為 inactive。
7. `EndCycle()`，`block.Write(image, manager.Publish(), manager.Status)`。

framework 在 PackML 掃描後才處理 alarm（FW: `FB_ModuleBase.TcPOU:843-844`），所以本次 scan 中進入 Clearing 的 service，它的錯誤在同一次 scan 已經被清除。

### Ack（AC5）
`ProcessAcknowledgement` 逐行對照 FW: `FB_ModuleAlarmManager.M_ProcessAcknowledgement`，步驟（同 issue AC5）：
1. 以上一次的 `ChangeRequest` 判斷上升緣（`R_TRIG`）。
2. `ChangeRequest` FALSE → `AckAccepted` FALSE、`AckError` None，結束（`AckResponseId` 保持）。
3. 不是上升緣 → 結束（回應保持）。
4. `AckResponseId` = `RequestId`，`AckAccepted` FALSE、`AckError` None。
5. `RequestId` 0 → `InvalidRequestId`；等於上一次記住的 RequestId → `DuplicateRequest`；其他 → 記住 RequestId（不論步驟 6 的結果，所以 `InvalidCommand` 的 RequestId 重送也得到 `DuplicateRequest`）。
6. `Command` 轉成 `AlarmAckCommand` 比較；`Command` 1：`MainErrorId` 0 → `AlarmNotFound`；`ServiceId` 0 找 configured 再找 hook，否則找 service；找不到 → `AlarmNotFound`。`Command` 2：Ack 全部。其他值（含負數）→ `InvalidCommand`。成功 → `AckAccepted` TRUE。
`Initialize` 之後第一次 scan，若 client 留下 `bChangeRequest` TRUE，視為上升緣並處理一次（同 PLC 重開機時 `R_TRIG` 從 FALSE 開始；與 PackML 的 `SeedInput` 不同，這裡照 framework）。

latch（`M_LatchState`）時 manager 覆寫 snapshot 的 `ModuleId`（`BeginCycle` 收到的值）、`ServiceId`（service alarm 用 entry 的、configured 與 hook 用 0）、`DateTime`（service 與 hook 用 entry 的 `DateTime`，configured 用 `utcDateTime` 參數）、`Active` TRUE、`Acknowledged` FALSE、`OccurrenceCount` 1；呼叫端傳入的這幾個欄位值不影響 latch 後的內容（`ServiceId` 仍用於下一段的回傳判斷）。

`Observe*` 回傳：加入或更新成功 → TRUE；`MainErrorId` 0、容量滿、hook 同 scan 重複 → FALSE；`ObserveServiceAlarm` 的 `ServiceId` 0、`ObserveHookAlarm` 的 `ServiceId` ≠ 0 → FALSE（framework 相同）。`Publish` 不改生命週期，只計算 latched count 與 Overflow（移除在 `EndCycle`、Ack、`UpdateConfiguredAlarm` 中發生）。`DuplicateId`、`Overflow` 在 `BeginCycle` 清為 0。

### 設定檔（AC12、13）
檔案是專案資料夾下的 `config/module-config.json`（`ModuleConfigPublisher.RelativePath`，#7），framework schema v4。`alarmList` 放在 `modules[]` 每個元素內，與 `variableList` 同層：

```json
{ "schemaVersion": 4, "modules": [ {
    "slot": 1, "id": 1, "enabled": true, "moduleType": "Polar2",
    "variableList": [ ], "configParamList": [ ],
    "alarmList": [ {
        "source": "ModuleVariableList[3].Value",
        "dataType": "REAL",
        "condition": { "operator": "gt", "value": 80.0, "tolerance": 0 },
        "mainErrorId": 101, "sourceErrorId": 0,
        "message": "FFU pressure out of range.", "severity": "Alarm" } ] } ] }
```

`slot` 是 `Chamber_Control` 的索引，`source` 相對於該 module（`GVL_Module.Chamber_Control[<slot>]`）。Polar2 目前的設定檔沒有 `alarmList`。
`ModuleConfigPublisher.Parse` 驗證 `alarmList`（不需要 symbol 表的規則），`Publish` 階段解析 source（需要 symbol 表）：

| 規則 | 訊息（前綴 `<path>: slot <n> alarmList`） | 階段 |
|---|---|---|
| `alarmList` 為 null 的元素 | `contains a null element.` | Parse |
| 筆數 > 30 | `has <k> entries, the limit is 30.` | Parse |
| 缺 `condition` | `mainErrorId <id> has no condition.` | Parse |
| `source` 空白 | `mainErrorId <id> has an empty source.` | Parse |
| `dataType` 無法解析 | `mainErrorId <id>: dataType '<x>' is not supported.` | Parse |
| `operator` 無法解析 | `mainErrorId <id>: operator '<x>' is not one of gt, lt, ge, le, eq.` | Parse |
| `severity` 不是 Alarm、Warning | `mainErrorId <id>: severity '<x>' is not Alarm or Warning.` | Parse |
| `mainErrorId` 0 或 ≥ 0xFFFF0000 | `mainErrorId <id> is outside 1..4294901759.` | Parse |
| 同 module 重複 `mainErrorId` | `mainErrorId <id> appears more than once.` | Parse |
| `<module path>.<source>` 解析失敗 | `cannot resolve <full path>: <error>` | Publish |
| symbol 型別與 `dataType` 不符（`AlarmCondition.Matches`） | `<full path> is <type>, not <dataType>.` | Publish |
| `message` 長度 > `ST_ExtAlarm.Message` 長度 | `mainErrorId <id>: message is <n> characters, the limit is 80.` | Publish |
| `<module path>.<source>` 長度 > `ST_ExtAlarm.Path` 長度 | `mainErrorId <id>: source path is <n> characters, the limit is 255.` | Publish |

`mainErrorId` 為負數或超過 uint 時，`JsonSerializer` 先丟 `JsonException`，訊息走現有的 `invalid JSON: …`（`ModuleConfig.cs:74-77`）。Parse 階段呼叫 `ParseOperator`、`ParseDataType` 與 severity 轉換只為驗證（`operator`、`dataType` 為 null 時視為無法解析，訊息中的 `<x>` 為空；`severity` 為 null 或省略時為 Alarm，同 §2.4 與 framework）；Publish 階段再呼叫一次產生 `ConfiguredAlarm`（純函式，結果相同），並對 resolve 後的 symbol 呼叫 `Matches`。規則依表格順序檢查，遇到第一個錯誤就失敗。`"alarmList": null` → `slot <n>: alarmList is null.`（同 `variableList`）。`Publish` 回傳 `ConfiguredAlarmTable`（原本 void），`PublishIfPresent` 包成 `ModuleConfigResult`。

只收 `enabled` 的 module（disabled module 的 snapshot 不 Ready，FW: `FB_ConfigValueSnapshotReader.TcPOU:40`）。沒有 `alarmList` 的 module → 空清單。結果放進 `ConfiguredAlarmTable`，key 為 `GVL_Module.Chamber_Control[<slot>]`。
