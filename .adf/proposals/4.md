# #4 Proposal：ADS sum 指令（0xF080–0xF082）與 symbol version 通知（0xF008）

Issue：https://github.com/KaiJuY/ADS_PLCSimulator/issues/4（「AC n」指其驗收條件第 n 條）。決策 log：`.adf/log/4.tsv`。前一個相關變更：#3（`.adf/proposals/3.md`；ADS、IG/IO、handle、process image、通知等名詞見其 §0）。

## 0. 名詞（補充 #3 §0）

| 名詞 | 意思 |
|---|---|
| sum 指令 | 一次 ADS ReadWrite 請求包含多個子項。IG 選擇種類（0xF080 sum read、0xF081 sum write、0xF082 sum read-write），IO = 子項數。 |
| 子項（item） | sum 內的一個單筆請求。請求資料先放所有子項的標頭，再放所有子項的寫入資料。標頭欄位都是 4 bytes little-endian：sum read 與 sum write 標頭 12 bytes = (IG, IO, 長度)；sum read-write 標頭 16 bytes = (IG, IO, 讀長度, 寫長度)。 |
| 單筆處理 | `PlcAdsServer` 對單一請求的處理：`OnReadAsync`（IG 0xF005 → `ReadByHandle`、IG 0x4040 → raw 讀取、其他 → base）、`OnWriteAsync`（0xF005 → `WriteByHandle`、0x4040 → raw 寫入、其他含 0xF006 釋放 → base）、ReadWrite（本類別目前沒有 override，全由 base：0xF003 建 handle、0xF004 依名稱讀；其他 IG 含 0x4040 回 `DeviceServiceNotSupported`）。 |
| 未知 handle | `TryResolveHandle`（#3）失敗：handle 不在 base 的 `handleTable`，或其 instance path 無法由 `SymbolTable.TryResolve` 解析。後者只在 symbol 表與 handle 表不一致時發生，正常執行不會出現。 |
| symbol version | IG 0xF008 的 1 byte 計數。Beckhoff 文件（`AdsSymbolVersionChanged`）：下載新 PLC 程式時改變；online change（PLC 執行中的小幅修改，不重新初始化 symbol 表）不變。模擬器由 base 的 `protected byte symbolVersion`（初始 1）回應。 |
| 超長 | 讀取或監看長度大於 symbol 大小（handle 讀、handle 通知 → 截斷為 symbol 大小）；寫入資料長度大於 symbol 大小（handle 寫 → `DeviceInvalidSize`，不寫）。規則來自 #3。 |

## 1. 目標

模擬器處理 sum read、sum write、sum read-write，並可訂閱 symbol version 通知，行為與 AMS 854 實測（issue #4 AC 1–9）相同。

## 2. 形狀

只改 `src/AdsPlcSimulator.Host/Ads/PlcAdsServer.cs`（`internal sealed class PlcAdsServer : AdsSymbolicServer`），沒有新的 public API。

新增 override（簽章與 factory 已查證，C8）：

```csharp
protected override Task<ResultReadWriteBytes> OnReadWriteAsync(AmsAddress sender, uint invokeId, uint indexGroup, uint indexOffset, int readLength, ReadOnlyMemory<byte> writeData, CancellationToken cancel);
```

新增成員：

```csharp
private const uint SumReadIndexGroup = 0xF080, SumWriteIndexGroup = 0xF081, SumReadWriteIndexGroup = 0xF082, SymbolVersionIndexGroup = 0xF008;

internal readonly record struct SumItem(uint IndexGroup, uint IndexOffset, int ReadLength, int WriteLength, int WriteOffset);
// 解析標頭並檢查長度（§4 G）。成功回 NoError，items 依序；WriteOffset = 該子項寫入資料在 request 內的位置。
internal static AdsErrorCode ParseSumItems(ReadOnlySpan<byte> request, uint count, bool readWrite, out SumItem[] items);

private async Task<ResultReadWriteBytes> SumReadAsync(AmsAddress sender, uint invokeId, SumItem[] items, int readLength, CancellationToken cancel);
private async Task<ResultReadWriteBytes> SumWriteAsync(AmsAddress sender, uint invokeId, SumItem[] items, int readLength, ReadOnlyMemory<byte> request, CancellationToken cancel);
private async Task<ResultReadWriteBytes> SumReadWriteAsync(AmsAddress sender, uint invokeId, SumItem[] items, int readLength, ReadOnlyMemory<byte> request, CancellationToken cancel);
```

`Subscription`（#3）增加 `public byte[]? FixedData { get; init; }`。設定時 `ScanAsync` 把 `FixedData` 複製到 `Buffer`，不讀 process image；`Offset` 填 0（不使用）。

## 3. 資料與狀態

sum 不新增狀態。子項依序 await 單筆處理（目前都同步完成），與單筆請求共用 process image 的鎖（每次 `Read`/`Write` 各自加鎖）與 handle 表。sum 不是原子操作：子項之間 workflow 可以寫入（854 是否原子未量測，client 不依賴）。

## 4. 行為

### A. 分派（`OnReadWriteAsync`）
IG 0xF080/0xF081/0xF082 → `ParseSumItems`，錯誤直接回；成功 → 對應的 sum 方法。其他 IG → `base.OnReadWriteAsync`（現況不變）。

### B. sum read（AC 1–3）
1. 檢查順序見 §4 G；其後 `readLength`（以 long 比較）必須**等於** `count × 4 + Σ 長度`，否則 `DeviceInvalidSize`（854 F080b 大 16 bytes、F080f 太小都拒絕）。
2. 每個子項呼叫 `OnReadAsync(sender, invokeId, ig, io, 長度, cancel)`（本類別的 override）。子項 IG 為 sum IG 時，該 override 交給 base → `DeviceServiceNotSupported`。
3. 回應 = `count` 個錯誤碼（4 bytes），接著每個子項一格「要求長度」的資料：成功 → 單筆結果複製到格子開頭（handle 超長時單筆已截斷為 symbol 大小），其餘補 0；失敗 → 錯誤碼為單筆結果，格子全 0。整體回成功（854 F080a）。

### C. sum write（AC 4–5）
1. 檢查順序見 §4 G；其後 `readLength < count × 4` → `DeviceInvalidSize`；較大可以（854 F081a），回應長度 = `count × 4`。
2. 每個子項呼叫 `OnWriteAsync(sender, invokeId, ig, io, 子項資料, cancel)`（本類別的 override），錯誤碼依序寫入回應。0xF006 子項由 base 釋放 handle（854 F081b）；handle 子項資料超長 → `DeviceInvalidSize`（854 F081a 第 4 項）；sum IG 子項 → base → `DeviceServiceNotSupported`。

### D. sum read-write（AC 6–7）
1. 檢查順序見 §4 G；其後 `readLength < count × 8 + Σ 讀長度` → `DeviceInvalidSize`。
2. 每個子項：IG 為 0xF080–0xF082（巢狀 sum）→ 不呼叫任何處理，結果 `DeviceServiceNotSupported`、長度 0（未量測；避免遞迴）。否則呼叫 `base.OnReadWriteAsync(sender, invokeId, ig, io, 讀長度, 子項寫入資料, cancel)`（直接呼叫 base，不重入本 override）。
3. 回應：先 `count` 組 (錯誤碼, 實際讀長度)，再接各子項實際讀到的資料，緊密排列；失敗項長度 0、不佔資料（854 F082a）。回應長度 = `count × 8 + Σ 實際長度`。
4. 實測對照：0xF003 名稱不存在 → `DeviceSymbolNotFound`/0；讀長度 ≠ 4 → `DeviceInvalidSize`/0（F082b）；0x4040 → `DeviceServiceNotSupported`/0（F082c）。base 已有這些行為（C4、existing-code reviewer 反編譯確認）。

### E. symbol version 通知（AC 8–9）
1. 讀取 IG 0xF008：維持 base（`readLength < 1` → `DeviceInvalidSize`；否則回 1 byte `[symbolVersion]`，C2）。
2. `OnAddDeviceNotificationAsync` 新增分支：IG 0xF008，`dataLength <= 0` → `DeviceInvalidWatchsize`（未量測，比照 #3 的 0 長度規則）；否則登記 subscription：`FixedData = [symbolVersion]`、`Buffer = new byte[1]`（監看長度 = min(dataLength, 1)，比照 handle 截斷）、模式依設定（OnChange 送一次初始值後因值不變不再送；Cyclic 依 CycleTime 重送同一 byte，與一般 Cyclic 一致）。
3. 刪除同 #3。

### F. 單筆 handle 錯誤碼（AC 2 的前提）
1. `ReadByHandle`、`WriteByHandle`（#3 新增；`OnReadAsync`/`OnWriteAsync` 在 IG 0xF005 時呼叫）：`TryResolveHandle` 失敗 → 回 `DeviceSymbolVersionInvalid`，不再交給 base（base 回 `DeviceSymbolNotFound`）。依據：854 單筆讀、寫從未發出的 handle 都回 `DeviceSymbolVersionInvalid`（量測 S1、S5）。
2. handle 通知不變：未知 handle 仍回 `DeviceInvalidOffset`（#3 量測 N8c）。
3. 854 對「同一連線剛以 0xF006 釋放的 handle」單筆讀取回 NoError（量測 S2），屬 handle 參照計數細節，不模擬。

### G. 標頭解析與檢查順序（`ParseSumItems`）
1. `count`（IO）以 uint 處理，所有長度以 long 計算。
2. `count == 0` → `DeviceInvalidSize`（F080c）。
3. 標頭總長 `count × 標頭大小 > request.Length` → `DeviceInvalidOffset`（F080e：IO=2 只送 1 項）。
4. 任一長度欄位 > `int.MaxValue` → `DeviceInvalidSize`（未量測；ADS 單筆長度實務上不超過 2 GB）。
5. sum read：`request.Length` 必須等於 `count × 12`，否則 `DeviceInvalidOffset`。sum write / read-write：`request.Length` 必須等於 標頭總長 + Σ 寫長度，否則 `DeviceInvalidOffset`。
6. 其後才由 §4 B–D 檢查 `readLength`。

## 8. 考慮過的做法

- sum 子項直接讀寫 process image（不經單筆處理）：否決。會複製 #3 的長度規則，兩處不一致時難以發現。
- sum read-write 子項重入本 override：否決。巢狀 sum 會遞迴；改為先擋 sum IG、其餘直接呼叫 base。
- 平行執行 sum 子項：否決。854 的子項順序與原子性未量測；依序執行最簡單、與單筆語意一致。
- symbol version 設成 8：否決。Allen 在 grill Q2 確認：值代表 symbol 表被換掉的次數，模擬器初始 1、執行中不變即可。
- 0xF008 通知用 process image 的位址：否決。symbol version 不在 process image 內；用 `FixedData`。

## 9. 不在範圍

- 其他 sum 指令：0xF083（sum read-ex）、0xF084 / 0xF085（sum 加入 / 刪除通知），以及巢狀 sum（回 `DeviceServiceNotSupported`）。
- symbol version 遞增（執行中換 symbol 表時才需要；epic #2 的 Host 執行模式若支援切換專案再做）。
- 「同連線剛釋放的 handle」的讀取行為（§4 F3）。

## 10. 風險

- §4 F 把單筆未知 handle 的錯誤碼從 `DeviceSymbolNotFound` 改為 `DeviceSymbolVersionInvalid`。TwinCAT client 可能把後者當作「symbol 表已換」而重新載入 symbol。真 PLC 對未發出的 handle 也回這個碼，所以這是貼近真機；client 只有在使用未知 handle 時才會遇到。stage I 以 AdsClientForPolarII 腳本確認綁定與操作不受影響。

## 與 issue 的差異

- 新決策：§4 F 改單筆未知 handle 的錯誤碼。issue AC 2 已補上。
- 新決策（未量測，比照既有規則）：0xF008 通知長度 0 → `DeviceInvalidWatchsize`、監看長度截為 1；巢狀 sum 子項 → `DeviceServiceNotSupported`；長度欄位 > int.MaxValue → `DeviceInvalidSize`。
