# Proposal #16：Polar2 service 自訂行為第 1 批 1b（serviceBehaviors、Mode 限制、參數檢查、SVID 寫入）

## 1. 目標
#16（https://github.com/KaiJuY/ADS_PLCSimulator/issues/16）：新設定檔 `config/service-behaviors.json` 讓 `service.host` 在 service 進入 Execute 時檢查 Module Mode 與參數範圍、以 ServiceParam 的 TIME 欄位當執行時間、並在 Execute 的進入、完成前、離開時寫 SVID。表外的 service 只受 Mode 規則限制；`trigger.onServiceExecute` 接管的 service 也只受 Mode 規則限制。

issue 的驗收條件（AC）：
- AC1：獨立檔 `projects/Polar2Chamber/config/service-behaviors.json`，含 module 層級 Mode 規則與 per-service 項目（參數範圍、執行時間欄位、進入／完成前／離開的 SVID 寫入；值為常數、ServiceParam 欄位、ECID，可取負值）。
- AC2：Run 時驗證（路徑、SVID/ECID id、欄位與型別、未知 key），失敗則 Run 失敗並說明原因；沒有檔案時不套用。
- AC3：表外 service 維持現狀，只受 Mode 規則限制。AC4：被 trigger 接管的 service 只套用 Mode 規則。
- AC5：進入 Execute 的那次 scan，Mode 不允許 → MainErrorId 2、SourceErrorId = Mode、Message `Not allowed in Mode 0 (Disable).`、Abort；不啟動 trigger 的 run。Mode 不是表中的整數 → SourceErrorId 4294967295。
- AC6：Polar2 規則：Disable 只允許 `Chamber.SetMode`；Manual 不允許 `Chamber.SingleProcess`、`Chamber.EMGS`；DryRun、Auto 全部允許。
- AC7：只在進入 Execute 時檢查 Mode。AC8：DryRun 時標記的 SVID 寫入值為 0。
- AC9：參數超出範圍 → MainErrorId 1、SourceErrorId = 值、Message `ArmIndex out of range (1~4).`、Abort；Mode 檢查先於參數檢查。
- AC10：ArmAlignTest、ArmTest：ArmIndex 1..4、NozzleIndex 1..3；FlowCalibration：ArmIndex 1..4、ArmNozzleIndex 1..3。
- AC11：ArmAlignTest、FlowCalibration 以 TestTime 為執行時間（須 > 0）；ArmTest 用 `defaultDelayMs`。
- AC12：完成前寫入（位置類）；進入 Execute 寫入、離開 Execute 寫 0（速度、流量類）；不做 ramp；ECID 值不是數字寫 0。
- AC13：MoveVelocityCW → SVID 53 = ECID 318，CCW 為負值，Stop 後 0。
- AC14：單元測試涵蓋 1–13。AC15：Integration 情境。AC16：不做真 PLC 量測。

現況缺口：今天 Polar2 的 145 個 service 中，除了 `Chamber.SetMode`、`Chamber.Initial`（各有 workflow），其他 service 不論 Module Mode、不論參數值都會進 Execute，NaturalCompletion 的在 `defaultDelayMs` 後 Complete，ExecuteUntilExternalStop 的等 Stop；SVID 不會隨動作改變。client（Handler、AdsClientForPolarII）因此無法驗證「Mode 不允許時被拒」「參數超出範圍時的錯誤」「設備動作時 SVID 的變化」。

名詞：
- **Run**（大寫）= 在 Host 啟動一個模擬器專案（建立 `SimulatorSession`，CLI 的 `--Simulator:ProjectPath` 或 `POST /api/project/run`）；Run 失敗 = 專案沒有啟動，API 回報原因。**run**（小寫）= workflow 的一次執行，例如 trigger fire 一次。
- **PackML 狀態**（`PackMLTypes.cs`）：Idle →（Start）Starting → Execute →（自然完成）Completing → Complete；Execute 中 Stop → Stopping → Stopped；Abort → Aborting → Aborted；Hold → Holding → Held →（Unhold）Unholding → Execute；Suspend／Unsuspend 同理。帶 -ing 的是「動作狀態」：每次 scan 問 hook 一次，hook 回傳 true 就到目標狀態。一次 scan 的順序是「處理命令 → 問目前動作狀態的 hook 一次」（`PackMLMachine.cs:86-92,184-190`）。`ServiceHost` 對 Starting、Execute 以外的動作狀態一律回傳 true（`ServiceHost.cs:378-379`）。所以由命令進入的 Starting、Aborting、Stopping 在同一次 scan 就問 hook；Starting 回 true 時同一次 scan 進 Execute，Aborting 同一次 scan 到 Aborted。由 Execute hook 進入的 Completing 要到下一次 scan 才被問，所以 Complete 在下一次 scan 出現。
- **service.host**：`ServiceHostNode`（`src/AdsPlcSimulator.Core/Flow/Nodes/ServiceNodes.cs:7-84`），每 10 ms 呼叫 `ServiceHost.Scan(image, now)`；`defaultDelayMs` 是 NaturalCompletion service 在 Execute 停留的時間（`ServiceHost.cs:384-386`），Polar2 為 5000（`projects/Polar2Chamber/workflows/Polar2_ServiceHost.flow.json`）。
- **ServiceCtrl / ServiceStatus / ServiceParam**：module 的三棵平行樹（`GVL_Module.Chamber_Control[s].ServiceCtrl.Chamber.ArmTest` 等）。ServiceCtrl 的葉節點是 `ST_ServiceCtrl`（client 寫 RequestId 與 PackML 命令）；ServiceStatus 的對應節點是 `ST_ServiceStatus`（`ServiceId`、`CompletionBehavior`、`PackMLOut.eStateCurrent`、`ErrorList`）；ServiceParam 的對應節點是 service 的參數 struct。**bound service** = identity file（`plc/ServiceIdentity/F_InitializePolarIIChamberServiceStatus.TcPOU`）給了 ServiceId ≠ 0 的 service；只有 bound service 會被 scan。**CompletionBehavior**：NaturalCompletion = 時間到自己完成；ExecuteUntilExternalStop = 停在 Execute 直到 Stop。
- **現行的 Execute 入口與 hook**（`ServiceHost.cs:374-418`）：`EnterExecute` 設 `ExecuteEntered = now`、`Generation = ++全域計數`、`EntryToken = _overrideToken(path)`、`CompletePending = false`、`ConfigParams?.Apply(image)`（#15 的 SetConfig 寫入 ECID）。Execute hook：被接管 → 等 workflow 的 `action.completeService`（`TakeCompletion`）；有 `ConfigParams`（SetConfig）→ 立刻完成；不是 NaturalCompletion → 不完成；否則 `now - ExecuteEntered >= defaultDelay` 時完成。
- **錯誤碼**（寫進 `ServiceStatus.<service>.ErrorList[n]` 的 `MainErrorId`、`SourceErrorId`、`Message`；#12 的 alarm 引擎同時把它列進 module alarm）：

  | MainErrorId | 意義 | SourceErrorId | Message 例 |
  |---|---|---|---|
  | 1 | 參數超出範圍或執行時間為 0 | 參數值 | `ArmIndex out of range (1~4).`、`TestTime must be greater than 0.` |
  | 2 | Mode 不允許 | Mode 值；Mode 文字不是表中的整數時 4294967295 | `Not allowed in Mode 0 (Disable).`、`Not allowed in Mode 'abc'.` |

  Message 超過欄位長度時由 `ServiceErrorList` 截斷（`AlarmImageLayout.cs:61` `Cut`）。
- **DryRun**：規格書 H3：DryRun 模式下設備照流程動作但不實際供液／供氣，所以流量、壓力 SVID 讀到 0。哪些 SVID 寫入屬於流量、壓力由設定逐條標 `dryRunZero`。第 1 批沒有這類項目。
- **Q4**（issue #16 決策紀錄）：Mode 不允許時，service 照樣進 Execute，在進入的那次 scan 加錯誤並 Abort；理由是 framework 沒有拒絕 Start 的機制，停在 Idle 的話 client 只看到逾時。**R7**：只在進入 Execute 時檢查 Mode，Execute 中 Mode 改變不中斷。**#10**（https://github.com/KaiJuY/ADS_PLCSimulator/issues/10）：規格待確認清單；Disable 允許 SetMode 是例外，記在那裡。
- **owner / int/16**：owner 是主持 ADF flow 的主 agent；`int/16` 是合併 U1、U2 後的整合分支。
- **ServiceHost**（`src/AdsPlcSimulator.Core/PackML/ServiceHost.cs`）：每個 bound service（ServiceId ≠ 0）一個 `ServiceUnit`，每個 module 一個 `ModuleUnit`；`ScanService` 每次 scan 跑一次 `PackMLMachine.Scan`。
- **PackML 狀態機**：`PackMLMachine.Scan(input, isActingStateDone)` 對目前的動作狀態呼叫一次 hook；Starting 的 hook 回傳 true 時同一次 scan 進 Execute，Execute 的 hook 從下一次 scan 才被詢問。`RequestCommand(Abort, modeRequestHigh)` 把命令排到下一次 scan；佇列已有命令或 mode request 為 high 時回傳 false。
- **AddFrameworkError**：`ServiceHost.cs:152-158`，把錯誤加入 service 的 `ErrorList`（#12 的 alarm 引擎把它變成 service alarm）；沒有 `ErrorList` 時不加入。
- **override / 接管**：workflow 的 `trigger.onServiceExecute` 登記 service 路徑；`ServiceHost` 以 `_overrideToken(ctrlPath)`（registry 的 `OverrideToken`）判斷。進入 Execute 時 token 不是 null 就是被接管（`EnterExecute`，`ServiceHost.cs:415`）。
- **trigger 的派送**：`trigger.onServiceExecute` 的參數是一個 ServiceCtrl 路徑（可含 `[#]`）；它監看對應的 `ServiceStatus.<service>.PackMLOut.eStateCurrent`，在某次寫入讓這個值從非 6 變成 6（Execute）時 fire（`ServiceNodes.cs:117-151`）。`ProcessImage.Written` 事件排進 channel，由 `FlowRuntime` 的背景迴圈呼叫 `TryFire`（`FlowRuntime.cs:11,19,33,126`），所以 trigger 判斷時 host 可能已經往後 scan。fire 時它向 host 讀 `ExecuteGeneration` 當成 run 的 `generation` 輸出（`ServiceNodes.cs:126`）。
- **SVID**：`ModuleVariableList : ARRAY[1..MaxModuleVariable] OF ST_ExtDescriptor`，`Value : STRING(80)`（`ST_ExtDescriptor.TcDUT:10`）。**ECID**：`ModuleConfigParamList : ARRAY[..] OF ST_ConfigParamDescriptor`，`ST_ConfigParamDescriptor EXTENDS ST_ExtDescriptor`，所以也有 `Value : STRING(80)`。兩者由 `ModuleConfigPublisher`（`src/AdsPlcSimulator.Host/Project/ModuleConfig.cs`）依 `config/module-config.json` 的順序發布：清單第 k 筆（從 1 起）寫到 `[k]`（`ModuleConfig.cs` `AddList`）。所以 id → 陣列位置要查 module-config。
- **Module Mode**：SVID 1 的 Value 文字。`Polar2_ModuleModeInit` 啟動時寫 `'1'`，`Polar2_Chamber_SetMode`、`Polar2_Chamber_Initial` 寫 `'0'`–`'3'`（`projects/Polar2Chamber/README.md:136-138`）。
- **Fail(path, reason)**：`ModuleConfigPublisher` 產生 `ModuleConfigException`（`ModuleConfig.cs:7,142`）；`SimulatorSession` 建構時丟出的例外讓 Run 失敗並回報訊息（`ProjectHost.cs:159-164`）。
- **U1、U2**：stage B 的一條鏈。U1 = Core 行為引擎；U2 = Host 設定檔。U3 = Integration 情境，合併後由 owner 在 int/16 做。

## 3. Data and state
- `ServiceBehaviorTable` 與其 record：Run 時由 Host 建立一次，之後唯讀，多個 host 共用。
- `ModuleRules`、`ServiceRules`：每次 `Initialize` 建立，存在 `ModuleUnit.Rules`、`ServiceUnit.Rules`，只在 host lock 內讀。
- `ServiceUnit.ExecuteRejected`、`EntryDryRun`、`EntryDuration`：在從 Starting 進入 Execute 時設定（§4.2），`ServiceUnit.Reset` 清為 false/false/null。只有 scan 執行緒（host lock 內）寫；`IsExecuteRejected` 在 host lock 內讀（trigger 的背景迴圈呼叫）。
- `ExecuteAbortPending`：Execute 入口被拒且 `RequestCommand(Abort)` 回傳 false 時設 true；Execute hook 重試成功時、`LeaveExecute` 時、`Reset` 時清除。
- `StartingAbortPending`：照舊（#15）。
- SVID Value 由 `ServiceRules` 以 `WriteSource.Workflow` 寫入，和 workflow 的 `action.writeSymbol` 相同。client 也可以寫 SVID；最後寫入者生效。

## 4. Behavior

### 4.1 Run（AC1、AC2）
1. `SimulatorSession` 建構：`ModuleConfigPublisher.PublishIfPresent` → `ServiceBehaviorLoader.LoadIfPresent`。
2. `service-behaviors.json` 不存在 → null，`ServiceBehaviors` 維持 `Empty`，`ServiceHost` 不檢查任何東西（AC2 後半）。
3. 存在但 `module-config.json` 不存在 → `Fail(path, "needs config/module-config.json to find SVID and ECID ids.")`。
4. `Parse`：`JsonSerializerOptions(JsonSerializerDefaults.Web) { UnmappedMemberHandling = JsonUnmappedMemberHandling.Disallow, NumberHandling = JsonNumberHandling.Strict }`：未知 key 與字串形式的數字（`"min": "1"`）都變成 `JsonException` → `Fail(path, "invalid JSON: ...")`。接著檢查（每條一個 `Fail`，訊息指出位置，例 `services.Chamber.ArmTest.ranges[1]`）：
   - **通則**：每個清單或字典欄位（`modes`、`services`、`allow`、`deny`、`ranges`、`onEnter`、`beforeComplete`、`onLeave`）寫成 `null` → `Fail`（省略 = 預設空清單，`modes` 例外：必須有且不可空）；清單元素或字典值為 `null` → `Fail`；字典 key、`allow`／`deny` 項目、mode `name` 在忽略大小寫後重複 → `Fail`。
   - `schemaVersion` 必須是 1；`modeSvid` > 0。
   - 每個 mode：`value` 不可 null、0 ≤ value ≤ 4294967294、不可重複；`name` 不可空白；`allow`、`deny` 恰好一個不是 null。
   - 每個 range：`field` 不可空白；`min`、`max` 不可 null；`min` ≤ `max`。
   - `duration` 寫了就不可空白。
   - 每個 SVID 寫入：`svid` > 0；`value` 不可 null；`constant`、`param`、`ecid` 恰好一個不是 null；`param` 不可空白；`constant` 必須是有限值。
5. `Build`：對 `module-config.json` 中每個 `enabled` 的 module（slot s，module path `GVL_Module.Chamber_Control[s]`，同 `ModuleConfigPublisher.ModulesRoot`）：
   - SVID id → 位置：`variableList` 中 id 相同的第 k 筆 → `ModuleVariableList[lower + k - 1].Value`（lower 是陣列下界，Polar2 為 1）。ECID 同理用 `configParamList` → `ModuleConfigParamList[...]`。找不到 → `Fail(path, "slot s: SVID 53 is not in module-config.json.")`。
   - `modeSvid` 的 SVID 必須存在（型別不限，Mode 讀文字）。
   - service 路徑（mode 的 allow/deny 與 `services` 的 key）：`{module}.ServiceCtrl.{key}` 必須解析成 `ST_ServiceCtrl`（`Unaliased.Name`）→ 否則 `Fail`。Host 不讀 identity file，所以不檢查 service 是否 bound（§4.1 步驟 6）。
   - **整數型別** = `Unaliased` 是 `PrimitiveType`，且 `Kind` 為 SInt、USInt、Int、UInt、DInt、UDInt、LInt、Byte、Word、DWord 其中之一；`EnumType`、ULInt、LWord 不算（ULINT 可能超過 long）。

   - `param` 值：field 必須是整數型別或 `PrimitiveKind.Real`／`LReal`。`ecid` 值：ECID 的 `dataType` 必須是 DINT 或 REAL。

### 4.2 進入 Execute（AC3–AC5、AC7、AC9、AC11）
`ScanService` 在 `Machine.Scan` 之後、`OnScanned` 之前：`before != Execute && state == Execute` → `EnterExecute(owner, service, before, image, now, modeRequestHigh)`；`before == Execute && state != Execute` → `LeaveExecute(service, image)`。

**檢查只在「從 Starting 進入」時做**（`before == Starting`，也就是一次 Start）。Unholding、Unsuspending 回到 Execute 是同一次動作的繼續：不檢查 Mode 與參數（AC7、R7），不重讀 duration，`ExecuteRejected` 維持 false，只重寫 `OnEnter`（離開到 Holding／Suspending 時 `OnLeave` 已把速度寫回 0，回到 Execute 時速度恢復）。

`EnterExecute`：
1. 照舊：`ExecuteEntered = now`、`Generation++`、`CompletePending = false`。
2. `object? token = _overrideToken(CtrlPath)`；`bool overridden = token is not null`。
3. `before != Starting`（Unhold／Unsuspend）→ `EntryToken = token`；`!overridden && EntryToken is null` 時 `Rules?.WriteOnEnter(image, EntryDryRun)`；結束（`ConfigParams?.Apply` 照舊，它自己會因 snapshot 已清空而不寫，#15 測試 `Unhold_back_to_Execute_does_not_write_the_batch_again`）。
4. 以下是從 Starting 進入：`ExecuteRejected = false`、`EntryDryRun = false`、`EntryDuration = null`、`ExecuteAbortPending = false`。`owner.Rules is null` → 跳到 8。
5. `owner.Rules.CheckMode(service.RelativePath, image, out bool dryRun)`：
   - 讀 Mode 文字。合法 = `long.TryParse(text, NumberStyles.AllowLeadingSign, InvariantCulture)` 成功且等於某條 rule 的 `Value`（"+1" = 1，"-0" = 0；"1.0"、" 1"、"" 不合法）。
   - 不合法 → `EntryCheck(2, 4294967295, $"Not allowed in Mode '{text}'.")`。
   - 合法：AllowOnly 且 service 不在清單，或 DenyListed 且 service 在清單 → `EntryCheck(2, unchecked((uint)value), $"Not allowed in Mode {value} ({name}).")`；否則 Pass，`dryRun = rule.DryRun`。（Host 已限制 value 在 0..4294967294。）
6. 通過 Mode 且 `!overridden` 且 `service.Rules is not null` → `CheckParams(image)`：
   - 依表的順序檢查每個 range：值 < Min 或 > Max → `EntryCheck(1, unchecked((uint)value), $"{Field} out of range ({Min}~{Max}).")`。
   - 再檢查 duration：TIME 值為 0 → `EntryCheck(1, 0, $"{DurationField} must be greater than 0.")`。TIME 是 32 位元無號毫秒（`ValueCodec.cs:54-55` 以 `ReadUInt32` 解碼），沒有負值，所以「> 0」就是「≠ 0」。
7. 任何一個不通過：`ExecuteRejected = true`；`EntryToken = null`（不接受 `action.completeService`）；`AddFrameworkError(service, image, check.MainErrorId, check.SourceErrorId, check.Message)`；`if (!Machine.RequestCommand(Abort, modeRequestHigh)) ExecuteAbortPending = true`；**不**呼叫 `ConfigParams.Apply`、不寫 SVID；結束。
8. 通過：`EntryToken = token`；`ConfigParams?.Apply(image)`（照舊）；`EntryDryRun = dryRun`（沒有 Rules 時 false）；`!overridden` 時 `EntryDuration = service.Rules?.ReadDuration(image)` 並 `service.Rules?.WriteOnEnter(image, dryRun)`。

結果（client 看到的）：進入 Execute 的那次 scan（N），`ErrorList` 多一筆、狀態寫成 Execute。scan N+1：`PackMLMachine.Scan` 先取出排好的 Abort 轉成 Aborting，同一次 scan 的 hook 對 Aborting 回傳 true，所以 scan N+1 結束時狀態是 Aborted（`PackMLMachine.cs:87-93`、`ServiceHost.cs:378-379`）。Aborting 不會被看到。若 mode request 為 high 使 Abort 排不進佇列，Execute hook 每次 scan 重試（同 #13 P1 A 的做法：P1 A = 內部 Abort 排不進佇列時每次 scan 重試）。

trigger：`ServiceExecuteTriggerNode.TryFire` 在 `EntersExecute` 為 true 之後問 `IsExecuteRejected`；為 true 就不 fire（AC5「不啟動 run」）。`ExecuteRejected` 在 scan N 的 `Status.Write` 之前就設好，所以 trigger 處理那次寫入時一定看得到。dispatch 是非同步的，若 trigger 處理寫入事件時 service 已經又進入一次新的 Execute，看到的是新那次的結果；這和現有 `ExecuteGeneration` 的讀取方式相同（§10）。

### 4.3 Execute 期間（AC11、AC12）
`IsServiceActingStateDone(Execute)` 的順序：
1. `ExecuteRejected` → 若 `ExecuteAbortPending` 且 `RequestCommand(Abort, modeRequestHigh)` 成功 → `ExecuteAbortPending = false`；回傳 false。Abort 一旦排入，下一次 scan 就離開 Execute，這個 hook 不會再被問。
2. overridden → `TakeCompletion()`（照舊）。
3. `ConfigParams is not null` → done = true（照舊）。
4. CompletionBehavior 不是 NaturalCompletion → false（照舊；duration 與 beforeComplete 對 ExecuteUntilExternalStop 沒有作用）。
5. done = `now - ExecuteEntered >= (EntryDuration ?? _defaultDelay)`。
6. 在 3 或 5 的 done 為 true 時，`service.Rules?.WriteBeforeComplete(image, EntryDryRun)`，然後回傳 true。這次 scan 結束時狀態是 Completing，Complete 在下一次 scan 才出現（AC12 的「Complete 出現之前」）。

Starting（SetConfig）完全照舊（`StartingChecked`、`StartingAbortPending`）。

### 4.4 離開 Execute（AC12、AC13）
`LeaveExecute`：`ExecuteAbortPending = false`；若 `!ExecuteRejected && EntryToken is null`（沒被拒、沒被接管）且 `service.Rules is not null` → `service.Rules.WriteOnLeave(image, EntryDryRun)`。離開的原因（Completing、Stopping、Aborting、Holding、Suspending）不區分。

注意：`EntryToken` 在被拒時也是 null，所以條件要同時看 `ExecuteRejected`。被接管的 Execute（`EntryToken` 不是 null）不寫。

### 4.5 SVID 寫入的值（AC8、AC12、AC13）
對每個 `SvidWrite`：
1. `DryRunZero && dryRun` → 0。
2. 否則依 `Kind`：Constant → `Constant`；Param → 讀 ServiceParam 欄位的數值；Ecid → 讀 ECID Value 文字，`double.TryParse(text, NumberStyles.Float, InvariantCulture)` 失敗或不是有限值 → 0。
3. `Negate` → 取負值（0 保持 0，不寫 "-0"）。
4. 文字：`IsReal` → `ConfigParamValue.Format(number.ToString("R", Invariant), Float32)`（和 #15 一樣：整數值補 ".0"）；否則 `Math.Round(number, MidpointRounding.AwayFromZero)` 轉成 long，夾在 DINT 範圍，`ToString(InvariantCulture)`。
5. `image.WriteValue(targetSymbol, text, WriteSource.Workflow)`。

## 8. Alternatives
issue 的考慮過的做法：
- 每個 service 一個 workflow：約 100 個 workflow。
- 節點路徑第二個萬用字元：改路徑解析，影響大。
- Mode 不允許時拒絕 Start、停在 Idle：framework 沒有拒絕 Start 的機制。
- ECID timeout 當執行時間：多數是報警值。
- 位置類 SVID 在 Complete 之後寫：client 可能讀到舊值（Q5）。
- 表放 `module-config.json`：generator 會覆蓋（R3）。
- MainErrorId 1 的 SourceErrorId 用欄位序號：與 SetMode 不一致（R6）。
- Execute 中 Mode 改變就 Abort：規格書沒有要求（R7）。

寫 proposal 時拒絕的做法：
- **在 Starting 檢查（像 SetConfig），被拒時不進 Execute**：trigger 自然不會 fire，不必加 `IsExecuteRejected`。拒絕原因：Allen 在 Q4 決定「進 Execute、addServiceError、Abort」。
- **trigger 改比對 generation**（`ExecuteEntry(path)` 回傳 (Generation, Rejected)）：可避免 §10 的競態，但現有 `generation` 輸出已有相同的競態，多一個 API 沒有解決主要情況。
- **SVID id 在 Core 從 image 的 `ModuleVariableList` 查**：Run 時無法驗證 id（AC2 要求 Run 失敗），且 Core 每次 Initialize 都要掃描。
- **新的例外型別 `ServiceBehaviorException`**：`ModuleConfigException` 已讓 Run 失敗並帶路徑，新型別沒有額外資訊。
- **Starting 與 Execute 入口共用一個 Abort 重試旗標**：`OnScanned` 在 Execute 時會清掉 Starting 的旗標（`ServiceHost.cs:685-686`），共用就要改 `ResetStarting` 的條件與 #15 的兩個 Stryker 註解；分開的旗標不動 #15 的程式。
- **Unhold／Unsuspend 回到 Execute 也重新檢查**：會讓 Held 期間改 Mode 的動作在 Unhold 時被 Abort，違反 R7 的「進行中的動作不中斷」。
- **Core 對表中未 bound 的 service 丟例外**：Host 不讀 identity file，擋不住；例外會變成 `service.host` 啟動失敗而不是 Run 失敗。未 bound 的 service 不會執行，略過不影響行為。
- **把 Starting 狀態搬進 `ConfigParamService`**（#15 structure review 的建議）：只減少約 20 行；把 `ServiceUnit` 搬到 partial 檔可減少約 190 行，且不改行為。

## 10. Risks
- trigger 非同步：若 trigger 處理一個 Execute 寫入事件時，service 已經被拒、Abort、Reset、又被接受地進入新的 Execute（需要 client 在 trigger 背景迴圈處理一個事件的時間內（通常數 ms）完成 Abort→Clear→Reset→Start，每一步至少一次 10 ms scan），trigger 會用新那次的狀態判斷。現有 `generation` 有相同的競態；預期 client 不會這麼快，沒有量測。
- client 看到一次 scan（10 ms）的 Execute，下一次 scan 直接 Aborted；只看 Complete/Aborted 的 client 不受影響。
- 啟動空窗：SVID 1 在 Run 時發布為 DINT 初始值 `"0"`（`ModuleConfig.cs:88`），`Polar2_ModuleModeInit`（`trigger.onStart`）寫 `'1'` 之前 Mode 是 Disable，這段期間只有 SetMode 能跑；`Polar2_ModuleModeInit` 載入失敗時一直如此。README 註明。
- `ServiceHost.Initialize`（重載 `Polar2_ServiceHost`）或 Retire 時，Execute 中的 service 不經過 `LeaveExecute`，`OnLeave` 不寫，SVID 53 可能停在速度值，直到下一次該 service 離開 Execute。和現在 workflow 重載時其他 SVID 不重設的行為相同。
- `duration`、`beforeComplete` 用在 ExecuteUntilExternalStop 的 service 時沒有作用，Host 在 Run 時無法發現（不讀 identity file）。README 註明。
- Mode 改成 0 後，只有 SetMode 能跑；手動測試若忘了寫回會讓後續操作都被拒。Integration 情境結束時寫回 1；README 註明。
- `service.host` 在 `Initialize` 丟 `ServiceHostException` 時，hosted 工作失敗的方式和 configured alarm 解析失敗相同（Host 已先驗證，正常不會發生）。
- 其他專案（RobustSolutionDemo）沒有 `service-behaviors.json`，行為不變。
