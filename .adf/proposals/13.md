# Proposal #13：Module heartbeat 與 Service Alive（持續執行意圖）檢查

## 1. 目標
#13（https://github.com/KaiJuY/ADS_PLCSimulator/issues/13）：模擬器照 RobustSolution framework 實作兩個用途不同的機制：
- **Module heartbeat**：client 定時更新 module 的 `HeartbeatIndex`；超過 timeout 沒更新，`ModuleStatus.IsControlSourceAlive` 為 FALSE。只設旗標。

## 4. Behavior

### Heartbeat（AC1–4）
- `ServiceHost.Initialize`：每個有 `Heartbeat` 的 module 呼叫 `Reset(image)`：`_lastIndex` = 目前 `HeartbeatIndex`、`_unchangedSince` = null、寫 `IsControlSourceAlive` TRUE。
- `ScanModule` 的第一步（framework `M_UpdateModule` 先做 `M_CheckHeartbeat`，FW: `POUs/10_Module/FB_ModuleBase.TcPOU:770-772`）：`Heartbeat?.Scan(image, now)`：
  1. 讀 `HeartbeatIndex`。與 `_lastIndex` 不同 → `_lastIndex` = 新值、`_unchangedSince` = `now`。`_unchangedSince` 為 null → 設為 `now`。
  2. `alive = now - _unchangedSince < timeout`（TON：經過時間 ≥ PT 時 Q 為 TRUE，FW: `:299-310`；framework 的 TON 在值改變的下一個 cycle 才重新計時，差一個 scan，對 10 s 無影響）。
  3. `alive` 與上次不同才寫 `IsControlSourceAlive`。
- 只寫這一個 BOOL；`StatusBlock`（ResponseId..PackMLOut）不涵蓋它，所以獨立寫。
- `TryCreate` 回傳 null 的 module 不做 heartbeat（AC4，同 #12 R6）。

### Service Alive（AC5–9）
順序照 framework `FB_ServiceBase.M_UpdateService`（FW: `POUs/20_Service/FB_ServiceBase.TcPOU:388-398`）：先判斷逾時、再處理待送的 Abort、最後跑狀態機。所以逾時的那一次 scan 就送出 Abort。`ScanService` 多一個參數 `AliveInput alive`（由 `ScanModule` 以新的 `ModuleUnit.ReadServiceAlive(service, moduleInExecute)` 取得，同既有的 `ReadServiceInput`，`ServiceHost.cs:706`），並只多呼叫一個私有方法 `ApplyAlive(service, alive, ref effective, image, now)`（在算出 `effective` 之後、記錄 `LastCommandRequest`/`LastModeRequest` 之前）；Machine.Scan 之後的 Enter/Leave 都由新的 `ServiceUnit.OnScanned(before, alive, settings, now)` 處理（它有 `AliveInput` 與設定；既有的 `EnterExecute(service, now)` 不變），`ScanService` 本身只多 2 個呼叫、不多分支。`Alive` 為 null 的情況由 `ServiceUnit` 的包裝方法處理（`ReadAlive` 回傳 default、`OnScanned`/`EvaluateAlive`/`TakeAbort` 直接返回），`ScanService` 不出現 `?.`。`ScanService` 目前 complexity 為 10（`.adf/baseline/crap.json`），改後必須 ≤ 12。

1. **判斷逾時**（FW: `M_EvaluateAliveTimeout`，`:222-257`）：`Alive.Evaluate(input, inExecute: Machine.State == Execute, now)`（`Machine.State` 是本次 scan 之前的狀態）：只有 `inExecute` 且 `_active` 時計算：`input.AliveIndex != _lastIndex` → `_lastIndex` = 新值、`_unchangedSince` = `now`；`now - _unchangedSince >= _timeout` 且 `!_timedOut` → `_timedOut` = TRUE、`AbortPending` = TRUE、回傳 `_timeout`（framework 的 TON 在改變的下一個 cycle 才重新計時，差一個 scan，`FB_ServiceBase.TcPOU:240`）。收到非 null 時，`ServiceHost` 用 private helper `AddFrameworkError(service, image, mainErrorId: 940, sourceErrorId, message)` 加入錯誤。`AddServiceError` 改為呼叫同一個 private builder `BuildServiceError(service, image, mainErrorId, sourceErrorId, message)`（組 `ExtAlarm`），`AddServiceError` 保留自己的 `RequireUsable` 與例外，`AddFrameworkError` 不丟例外（欄位：ModuleId 從 `_moduleByService[...].Alarm?.ReadModuleId(image)`，沒有 alarm 欄位時為 0；ServiceId；Path = `service.StatusPath`；Severity Alarm；DateTime = `AlarmClock.Format(_utcNow())`）。SourceErrorId = `(uint)_timeout.TotalMilliseconds`（同 FW `TO_UDINT(_ActiveAliveTimeout)`；TIME 是 4 byte 毫秒值，`PlcTypes.cs:75`，限制後的值不會超過 uint，不會溢位）；Message `Service Alive timeout expired.`。`Errors` 為 null、重複、已滿時不加入（`Add` 不丟例外），Abort 照做。只有 `Add` 回傳 `Added` 時才 `WriteIfChanged`（同 `AddServiceError`，`ServiceHost.cs:121-122`）。
2. **待送的 Abort**（FW: `M_PreparePackMLInput`，`:289-300`）：`Alive.AbortPending` 為 TRUE 時，`effective` 的 `ModeRequest` 改為 FALSE，並呼叫 `service.Machine.RequestCommand(PackMLCommand.Abort, modeRequestHigh: false)`；回傳 TRUE → `ClearPendingAbort()`。回傳 FALSE（佇列已有其他內部命令）→ 下一次 scan 再試；service 已離開 Execute 也照樣再試（P1 A，與 framework 相同）。`LastModeRequest` 記錄的是壓低後的值（`ApplyAlive` 在記錄之前執行），所以 Abort 待送期間 workflow 的 `action.abortService` 不會因 client 的 mode request 而被拒，與 framework 覆寫 `PackMLIn` 後的行為相同。強制 mode request 為 FALSE 會讓 `ClearLatches` 重設 `_modeConsumed`，client 若一直拉高 mode request，Abort 之後會被當成新的請求處理一次，與 framework 相同。
3. **Machine.Scan 之後**，用已有的 `before` 與 `Machine.State`：
   - 由非 Execute 進入 Execute（與 `EnterExecute(service, now)` 同一處）→ `Alive.EnterExecute(input, service.Behavior, settings, now)`：`_active` = behavior 為 `ExecuteUntilExternalStop` 且 `input.AliveTimeout > 0`；`_timeout` = `settings.Clamp(input.AliveTimeout)`；`_lastIndex` = `input.AliveIndex`；`_unchangedSince` = `now`；`_timedOut`、`AbortPending` = FALSE（FW: `M_InitializeAliveMonitoring`，`:260-285`）。
   - 不在 Execute → `LeaveExecute()`：`_active` = FALSE（`AbortPending` 保留）。

情境對照（Allen 確認）：同一次 scan 逾時且 client 送 Stop → 內部 Abort 優先（`SelectCommand`），service 到 Aborted；client 的 Stop 在下一次 scan 才處理，Aborted 不接受 Stop → `CommandRejected`。已在 Stopping 或 Stopped 的 service 不會判斷逾時，所以不會 Abort。

- `input` 由 `Alive.Read(serviceCtrlBlock, moduleInExecute)` 取得：module 不在 Execute 時為 (0, 0)（FW: `POUs/10_Module/FB_ServiceCoordinator.TcPOU:314-367`）。已在監控中的 service 繼續用進入 Execute 時記下的 `_timeout`；`AliveIndex` 讀 0，與上次不同時算一次更新。
- workflow 接管的 service（`IsOverridden`）走同一條路徑（AC9）。
- `Initialize` 時對每個 bound service 呼叫 `Alive?.Reset()`。
- `AliveIndex`、`AliveTimeout` 從已讀入的 `_serviceCtrlBuffer` 解碼（`ModuleUnit.ReadInputs` 已讀整個 `ServiceCtrl` 區塊），不另外讀 image。

### timeout 來源（AC10）
`AliveSettings.FromSymbols`：`TryGetConstant("Param_Config.ModuleHeartbeat_Timeout")` 等三個；值不是 `TimeSpan` 或 ≤ 0 → 用 `Default` 對應欄位；`ServiceAliveMin > ServiceAliveMax` → `ServiceHostException("Param_Config.ServiceAliveTimeoutMin (<a>) is greater than ServiceAliveTimeoutMax (<b>).")`，用了預設值的一方在值後加 ` (default)`。只有 `T#` 字面值會是 `TimeSpan`；`T#5S * 2` 這類運算式在 builder 中算成 long，視為「不是 TIME」而用預設值（README 註明）。

### 驗證（AC11–13）
- 單元測試：第 6 節。
- 853（stage I，R4）：只寫 `GVL_Module.Chamber1_Control[1].HeartbeatIndex`，不碰其他欄位：(0) 在 3 s 內每 500 ms 讀 `HeartbeatIndex`，任何一次值不同表示有其他 client 在寫 → 停止並回報；(1) 讀原值與 `IsControlSourceAlive`，先把原值印出來（中斷時可手動寫回）；(2) 每 200 ms 遞增，持續 2 s，讀 TRUE；(3) 停止，每 200 ms 讀，記錄變成 FALSE 的時間（預期 10 s ± 0.5 s）；這段期間若讀到不是本程式寫的值，結果作廢；(4) 只有當 `HeartbeatIndex` 仍是本程式最後寫入的值時才寫回原值（寫回本身是一次變化，`IsControlSourceAlive` 會變 TRUE 再於 10 s 後回到 FALSE，等同原狀）。步驟 (3) 期間 853 的 `IsControlSourceAlive` 會短暫為 FALSE，這是預期的副作用；framework 沒有其他程式讀它。模擬器以同一程式（`--port 25860 --root GVL_Module.Chamber_Control[1]`）得到相同結果。
- Integration driver 新增，排在 S12 之後、S15 之前（S15 讓 module 1 停在 Stopped，之後 service 不會進 Execute；也不可插在 S11 與 S16 之間）；S17 計時從最後一次寫入算起，每 200 ms 讀一次：
  - **S17 Heartbeat**：遞增 `HeartbeatIndex` 2 s → `IsControlSourceAlive` TRUE；停止 → 9 s 時仍 TRUE、11.5 s 內變 FALSE。
  - **S18 Service Alive**：`Holder.Rotate.MoveVelocityCW` 設 `AliveTimeout` = T#500MS、`AliveIndex` 不變，Start → 1.5 s 內 Aborted；`ModuleAlarmList` 有 ServiceId = 該 service、MainErrorId 940、SourceErrorId 500；Clear → Reset 回 Idle。再以 `AliveTimeout` T#500MS、先開始每 100 ms 遞增 `AliveIndex`，然後 Start（避免等 Execute 時超過 500 ms），持續 2 s → 仍 Execute；S18 開始前用 `RequireIdleAsync` 確認 `HolderMove` 為 Idle；Stop → Stopped → Reset → Idle；`AliveTimeout` 寫回 0。

## 8. Alternatives

- 拆成兩個 issue：不採用（Q5 A）。
- service 離開 Execute 就取消待送的 Abort（P1 B）：不採用，與真 PLC 不同；改成 framework 的順序後，只有佇列已有其他命令時才會保留到下一次 scan（Allen 2026-10-31 選 A）。
- 逾時判斷放在狀態機之後、Abort 晚一個 scan：不採用，與 framework 順序不同（correctness reviewer）。
- timeout 寫死：不採用（Q3 A）。
- 853 驗證 Service Alive：不採用，853 的 ExecuteUntilExternalStop service 只有軸類（Q4、R4）。
- 常數在 `PlcProgram` 而非 `SymbolTable`：不採用，`service.host` 只拿得到 `NodeSettings.Symbols`（`SymbolTable`），且 enum 值已放在 `SymbolTable`。
- 全部常數都必須能計算、否則建置失敗：不採用，會讓目前能載入的專案失敗。
- Service Alive 的 Abort 用 `ServiceHost.Abort`：不採用，它在排不進去時丟例外、而且帶 `LastModeRequest`；framework 要壓低 mode request 並重試。
