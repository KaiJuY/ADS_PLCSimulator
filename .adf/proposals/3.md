# #3 Proposal：ADS 部分讀寫照真 PLC 行為處理、Polar2 slot 1 發布 identity

Issue：https://github.com/KaiJuY/ADS_PLCSimulator/issues/3（下文「AC n」指該 issue 的驗收條件第 n 條）。決策 log：`.adf/log/3.tsv`。

## 0. 名詞

| 名詞 | 意思 |
|---|---|
| ADS | Beckhoff 的通訊協定。client 以 (IndexGroup, IndexOffset, 長度) 讀寫 PLC。 |
| IG / IO | IndexGroup / IndexOffset。 |
| IG 0x4040 | PLC 資料區（`PlcAdsServer.PlcDataIndexGroup`）。IO 是資料區內的 byte 位址。 |
| IG 0xF003 | 依名稱建立 variable handle。回傳一個 handle 編號。 |
| IG 0xF005 | 以 handle 讀寫：IO 是 handle 編號。 |
| IG 0xF006 | 釋放 handle：寫入 4 bytes 的 handle 編號。 |
| IG 0xF008 | symbol version；client 訂閱它來偵測 online change（#4 處理）。 |
| 通知（notification） | client 訂閱一段位址，server 在值改變（OnChange）或定時（Cyclic）時主動送出資料。送出的單位是 stamp（一個時間戳）內含 sample（通知 handle + 資料）。 |
| process image | `AdsPlcSimulator.Core.Plc.ProcessImage`：模擬 PLC 的整塊記憶體（byte 陣列，`Size` 為總長）。 |

| client write | 以 `WriteSource.Client` 寫入 process image；會觸發 workflow 的 `trigger.onClientWrite`。 |
| workflow 節點 | `trigger.onStart`（workflow 載入後執行一次）、`flow.forLoop`（`index` 從 from 到 to）、`action.writeSymbol`（寫一個 symbol；路徑中的 `[#]` 用 `index` 輸入取代）。定義在 `src/AdsPlcSimulator.Core/Flow/Nodes/`。 |
| AMS 854 | 本機 TwinCAT runtime 上的真 PLC（Plc30 App，與 Polar2 相同的 `GVL_Module`），Allen 授權用來量測。 |
| AdsClientForPolarII | `tests/AdsClientForPolarII/`（未進版控的 binaries），Allen 的 PolarII client（BATW.ModuleController.Sdk）。 |
| U1 / U2 | stage B 的兩個實作單位：U1 = ADS server（第 4 節位址對應與 A–E），U2 = Polar2 identity（第 4 節 F）。 |

## 1. 目標

讓模擬器的 ADS server 對讀、寫、通知的長度規則和真 PLC（AMS 854 實測）一致，通知在值改變時真的送出；並讓 Polar2 slot 1 在開機時發布 identity，使 AdsClientForPolarII 能綁定。

## 2. 形狀

核心改動是一個型別：`src/AdsPlcSimulator.Host/Ads/PlcAdsServer.cs` 的 `internal sealed class PlcAdsServer : AdsSymbolicServer`。沒有新的 public API。另外修改一個 workflow 資料檔、兩個測試檔、兩份文件（第 5 節）。

新增的 override（回傳型別與 factory 已查證，見 C9）：

```csharp
protected override Task<ResultReadBytes> OnReadAsync(AmsAddress sender, uint invokeId, uint indexGroup, uint indexOffset, int readLength, CancellationToken cancel);
protected override Task<ResultWrite> OnWriteAsync(AmsAddress sender, uint invokeId, uint indexGroup, uint indexOffset, ReadOnlyMemory<byte> writeData, CancellationToken cancel);
protected override Task<ResultHandle> OnAddDeviceNotificationAsync(AmsAddress sender, uint invokeId, uint indexGroup, uint indexOffset, int dataLength, AmsAddress receiver, NotificationSettings settings, CancellationToken cancel);
protected override Task<ResultAds> OnDeleteDeviceNotificationAsync(AmsAddress sender, uint invokeId, uint hNotification, CancellationToken cancel);
protected override void OnConnected();          // 先呼叫 base.OnConnected()，再啟動通知迴圈（簽章以 base 為準）
protected override void Dispose(bool disposing); // 停止通知迴圈
```

結果一律用 `ResultReadBytes.CreateSuccess(ReadOnlyMemory<byte>)`、`ResultWrite.CreateSuccess(invokeId)`、`ResultHandle.CreateSuccess(handle)`、`ResultAds.CreateSuccess(invokeId)`，失敗用各自的 `CreateError(AdsErrorCode)`。

新增的 private 成員：

```csharp

private sealed class Subscription                                            // 只在 _subscriptionLock 內讀寫可變欄位
```

## 3. 資料與狀態

| 狀態 | 擁有者 | 誰改 | 執行緒 |
|---|---|---|---|
| process image | `ProcessImage` | client 寫入（本檔）、workflow | `ProcessImage` 自己的鎖；一次 `Read` 是一致的快照 |
| handle 表 | base `handleTable` | base（建立、釋放） | ADS 收訊執行緒 |
| `_subscriptions` | `PlcAdsServer` | Add/Delete（ADS 收訊執行緒）、`NotifyLoopAsync` | `_subscriptionLock`（`lock`）。迴圈在鎖內複製清單，**送出時不持鎖** |

通知迴圈生命週期：`OnConnected` 啟動一次（`_notifyLoop ??=` 在 `Interlocked.CompareExchange` 保護下）。`Dispose(true)` 先 `_notifyStop.Cancel()`，等 `_notifyLoop` 最多 1 秒，再清空 `_subscriptions`，最後呼叫 base。`OnDisconnect` 不停迴圈（它表示 server 與 router 斷線，不是 client 斷線）。

## 4. 行為

### 位址對應
現況：`OnCreateSymbols` 為每個 root 建 `DataArea(root.Path, 0x4040, root.Offset, size)`，並存 `_coreOffsetMinusAdsOffset[root] = root.Offset - adsIndexOffset`；`TryLocate` 往上找到 root，用 `symbol.IndexOffset + delta` 算 process image 位址。
新：因為 DataArea 是以 `root.Offset` 建立，delta 恆為 0（C1、C10）。移除 `_coreOffsetMinusAdsOffset`；ADS IO = process image offset。`OnCreateSymbols` 在 delta ≠ 0 時丟 `InvalidOperationException`，訊息含 root 名稱、core offset、ADS offset。這是程式不變式（由同一行程式建構），不是對使用者專案的假設。`TryLocate` 刪除，改用 `TryResolveHandle` / `_symbols.TryResolve`。仍走 base 的路徑（例如依名稱讀寫 0xF004 → `OnReadRawValue`/`OnWriteRawValue`）改成 `_symbols.TryResolve(symbol.InstancePath)` 取 offset，保留 `length <= size` 檢查，找不到 → `DeviceSymbolNotFound`（與現況相同）。

### A. handle 讀（AC 1–3）— `OnReadAsync`，IG 0xF005
1. `TryResolveHandle` 失敗 → `base.OnReadAsync`（保留 base 錯誤碼）。
2. `readLength < 0` → `DeviceInvalidSize`。
3. 讀 `min(readLength, size)` bytes（一次 `ProcessImage.Read`），回成功。`readLength == 0` 回 0 bytes。

### B. IG 0x4040 讀（AC 4）— `OnReadAsync`
`readLength < 0` → `DeviceInvalidSize`（與 A2 一致）；`TryResolveRaw` 失敗 → `DeviceInvalidOffset`；成功 → 讀 `readLength` bytes。可跨 symbol、從 symbol 中間開始。其他 IG 一律 `base.OnReadAsync`。

### C. 寫（AC 5–7）— `OnWriteAsync`
1. IG 0xF005：handle 不存在 → base。`length > size` → `DeviceInvalidSize`，不寫。`length == 0` → 直接回成功，**不呼叫 `ProcessImage.Write`**（避免 0 長度寫入觸發 `trigger.onClientWrite`）。否則寫前段，`WriteSource.Client`。
2. IG 0x4040：`TryResolveRaw` 失敗 → `DeviceInvalidOffset`；`length == 0` → 成功、不寫；否則寫入，`WriteSource.Client`。
3. 其他 IG（含 0xF006 釋放）→ base。

### D. handle 釋放（AC 10）
2026-10-30 實測：模擬器（base）已接受 `IO=handle, data=handle` 的釋放（`NoError`）。差異只在錯誤碼：

| 情況 | 模擬器 | 854 |
|---|---|---|
| 釋放從未發出的 handle | `DeviceInvalidParam` | `DeviceSymbolVersionInvalid` |
| 重複釋放（H10c；模擬器值來自 2026-10-30 base probe「release IO=0 same handle again」） | `DeviceInvalidParam` | `DeviceInvalidOffset` |
| data 3 bytes | `DeviceInvalidSize` | `DeviceInvalidSize` |

本 issue 不改釋放的程式；AC 10 改為：以測試鎖住 `IO=handle` 釋放成功（回歸測試）。錯誤碼差異記為已知差異（client 不依賴它），不在範圍。client 那 501 次失敗的原因在 stage I 用 log 確認（預期是重複釋放）。

### E. 通知（AC 8、9、9a）
`OnAddDeviceNotificationAsync`（依序檢查）：
1. 其他 IG（0xF008 等）→ base（#4 處理）。
2. IG 0xF005 且 handle 不存在 → base（保留 base 錯誤碼）。
3. `dataLength <= 0`（在登記之前檢查）：IG 0xF005 → `DeviceInvalidOffset`；IG 0x4040 → `DeviceInvalidWatchsize`（854 實測 N0a、N0b）。**假設**：負長度比照 0（未量測，client 不會送）。
4. IG 0xF005：`dataLength > size` → `DeviceInvalidOffset`（N8b）。否則登記 `(offset, dataLength)`。
5. IG 0x4040：`TryResolveRaw` 失敗 → `DeviceInvalidOffset`；否則登記。
6. 模式（Cyclic 在 854 實測 N9c：100 ms、值不變，1 秒 6 筆）：`Cyclic`、`ServerCycle`、`ClientCycle` → Cyclic；其他（`OnChange`、`ServerOnChange`、`ClientOnChange`…）→ OnChange。`Interval = max(settings.CycleTime ms, 10 ms)`。`MaxDelay` 不處理。
7. 登記時 `LastSent = null`、`NextDue = now + 20 ms`，回 `ResultHandle.CreateSuccess(handle)`。**初始值只由迴圈送**，而且最早在登記後 20 ms，確保 client 先收到 Add 回應（回應在同一呼叫鏈內送出，遠小於 20 ms）。

`OnDeleteDeviceNotificationAsync`：handle 在 `_subscriptions` 且 `Receiver == sender` → 移除、回成功；handle 在 `_subscriptions` 但 sender 不符 → `DeviceNotifyHandleInvalid`；不在 → `base.OnDeleteDeviceNotificationAsync`（base 會回 `DeviceNotifyHandleInvalid`，實測與 854 一致）。刪除後最多還可能有一筆已在送出中的 sample。

`NotifyLoopAsync`（`PeriodicTimer` 10 ms；Windows 計時器解析度約 15 ms，只保證「不早於 Interval」）：
1. 在鎖內取出 `NextDue <= now` 的 subscription 清單，對每一個以一次 `ProcessImage.Read` 讀進 `Buffer`。
2. 決定是否送：`LastSent == null`（初始值）、或 Cyclic、或 `Buffer` 與 `LastSent` 不同。送出後在鎖內更新 `LastSent`（複製）並設 `NextDue = now + Interval`（不補送）。
3. 送出（不持鎖）：`DeviceNotificationRequestAsync(Receiver, invokeId: Interlocked.Increment(ref _nextInvokeId), 1, [new NotificationSamplesStamp(DateTimeOffset.UtcNow, [new NotificationDataSample(handle, data)])], 1 秒逾時並與 _notifyStop 連結的 token)`（`CancellationTokenSource.CreateLinkedTokenSource` + `CancelAfter`，讓 Dispose 不必等滿逾時）。
4. 回傳非 `NoError`、或丟例外（不含迴圈取消）→ 在鎖內移除該 subscription，`_logger.LogWarning` 記 receiver、handle、原因。單一 subscription 的例外不會中止迴圈。
5. `OperationCanceledException`（`_notifyStop`）→ 結束迴圈。

### F. Polar2 identity（AC 11，U2）
`Polar2_ModuleModeInit.flow.json`：拆掉 `start → loop` 連線，改成 `start → idModuleId → idEnabled → idModuleType → loop`。三個新節點都是 `action.writeSymbol`，路徑固定 `[1]`（不接 `index`）：

| 節點 id | symbol（型別） | value |
|---|---|---|
| `idModuleId` | `GVL_Module.Chamber_Control[1].ModuleStatus.ModuleId`（UDINT） | `1` |
| `idEnabled` | `GVL_Module.Chamber_Control[1].ModuleStatus.Enabled`（BOOL） | `TRUE` |
| `idModuleType` | `GVL_Module.Chamber_Control[1].ModuleStatus.ModuleType`（STRING(16)） | `Polar2` |

座標放在 `start` 和 `loop` 之間的一列（y = 200）。迴圈與它寫的 SVID 不變。沒有其他程式碼或 workflow 寫這三個欄位（C11）。README 的 Workflow 段落補一句 slot 1 identity。

## 8. 考慮過的做法

- 只修 handle 讀取：Allen 否決（issue #3）。
- 依推測規則：Allen 否決，以 854 實測為準（issue #3）。
- 6 個 slot 都設 live、ModuleType 留空：Allen 否決（issue #3）。
- 通知用 `ProcessImage.Written` 事件即時送：否決。事件在寫入者執行緒觸發，送網路會拖慢寫入者，也做不到 CycleTime 與 Cyclic。
- 讓 base 處理通知：否決。base 的通知以 symbol 為單位，不支援 IG 0x4040（C10），也看不到 process image 的變更（C5）。
- 保留 `_coreOffsetMinusAdsOffset`：否決。delta 由同一行程式建構恆為 0，保留它會讓 IG 0x4040 的原始位址需要另一套對應；改成啟動檢查，違反時訊息指出 root 與兩個 offset。
- 在 Add 回應前送初始值：否決，client 會丟掉它還不認識的 handle 的 sample。
- 平行送出通知：否決。目前只有單一 client；改成每筆 1 秒逾時，最壞情況延遲有界。
- 模擬釋放錯誤碼的差異：不做。要追蹤「曾經發出但已釋放」的 handle，client 不依賴這些錯誤碼。

## 9. 不在範圍

- sum 指令 0xF080–0xF082、symbol version 通知 0xF008（#4）。
- 釋放 handle 的錯誤碼差異（第 4 節 D）。
- `MaxDelay` 的批次語意；client 斷線時主動清除通知（只在送出失敗時移除）。
- `eModeCurrent` 初始值、heartbeat、ModuleId 唯一性檢查。

## 10. 風險

- 通知迴圈每 10 ms 讀被訂閱的範圍：每個 subscription 重用一個 buffer，只在送出時配置 `LastSent`。Cyclic 訂閱 11684 bytes、每 10 ms 一次約 1.1 MB/s 網路量，屬 client 自己要求的量。
- 一個不回應的 client 最多讓其他 subscription 延遲 1 秒（逾時），之後被移除。
- 啟動檢查若失敗會讓 Host 啟動失敗（`AdsServerService` 重新丟出）。訊息指出 root 與 offset；由於 delta 由同一行程式建構，只有 TwinCAT 套件改變 DataArea 語意時才會發生。
